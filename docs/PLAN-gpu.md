  OpenCL 3.0 运行时可枚举 ⇒ **两条路线本机都能验**（wgpu 走 D3D12/Vulkan，NVIDIA 路径也有硬件）。

## 4. 确定性口径（**crux**；三条可选，附推荐）

骨架已给出仓库自己的口径：**"必须 CPU 回退且结果一致（同档参数下位姿哈希一致，
容差 = 严格模式量化容差）"** ⇒ 即**量化哈希 + 容差**，不是逐位一致。三条路：

| 口径 | 做法 | 优 | 劣 |
|---|---|---|---|
| **A 决定性设计** | GPU 内核内**固定序累加**（每格/每邻域按索引序串行求和、**不用原子加**） | 可与 CPU **位级一致**（与我这轮 CPU 并行化同一原则） | 慢一些（放弃原子/乱序归约） |
| **B 量化哈希门**（骨架口径） | 位置/速度**量化后**比哈希，容差 = 严格模式量化容差 | 允许浮点顺序差 ⇒ GPU 可用最快写法 | 不是位级 ⇒ 需定义量化步长与容差表 |
| **C 报告档** | 像 wasm/arena 那样只报数、不入门 | 零约束 | 无回归保护 |

**推荐**：**A 优先、B 兜底**——能位级就位级（密度/力这类逐粒相位天然可以），做不到的相位
（跨粒归约，如 PBF 的密度约束全局迭代）用 B 并在档里**逐相位写明用的是 A 还是 B**。

## 5. CI 策略（决策点②）

CI runner **无 GPU** ⇒ 建议：① CI 照旧跑 CPU 档（不变）+ 编译/测试 GPU crate 的 **CPU 回退路径**
（保证不断链）；② GPU 实测走**本机门**（照 wasm/arena 先例：本地命令 + JSON 基线入库 + 记机器指纹
——本机 RTX 4060 Ti 可验）；③ 是否把"GPU 档不在 CI 内"写成正式口径，需拍板。

## 6. 首里程碑（M4 step 1，**最小可测**，不做 PBF/FLIP 全档）

**"GPU 版密度 + 力相位"**（与现有 WCSPH **同数学、同场景、同哈希口径**）。理由：
1. 与 CPU **天然对拍**——我这轮已有的仪器正好用：30 万粒规模探针（`sph_scale`）、相位计时
   （`phase_us`）、并行/串行逐位门（`parallel_equals_serial_bitwise`）；
2. 复用**同一份状态布局**（SoA `pos/vel/dens/press/pmass` + 计数排序网格）⇒ 苹果对苹果；
3. 它的读数**决定 PBF/FLIP 值不值得按 SPEC 全做**（若 GPU 在 30 万粒上给不出数量级优势，
   就该回头谈档位，而不是照抄规格）。

**判据（首里程碑）**：① 一致性——同场景 CPU/GPU **量化哈希一致**（或位级，按 §4 的 A/B）；
② 性能——GPU ms/tick 与对 CPU（8 线程 124 ms/300k）的**加速比**；③ 显存——按 §3 的
≤400 B/粒 预算核对实测占用；④ 不与单一厂商绑定（wgpu 路径在 Intel iGPU 上也要跑通）。

## 7. 前置与风险

- **rust-gpu 工具链**：nightly 依赖 + 构建脚本改动（CI 与本机都要）；可先考虑"**预编译 SPIR-V
  入库**"降低工具链耦合（待选型）；
- **wgpu 版本钉法**：本仓依赖纪律（棘轮 + 理由），需与 §3 的基线更新一并办；
- **显存预算**：10M 粒 ≤4 GB ⇒ 每粒 ≤400 B——PBF 需 `pos/vel/den/pres`（4×16 B = 64 B）+ 邻域
  索引 + 迭代 scratch ⇒ **要真算一遍**（首里程碑后给出实测表）；
- **与 CPU 档的界面**：`PhysGpuBackend` 已有 trait；耦合（刚体↔流体）在 GPU 档大概率仍是
  "GPU 流体 + CPU 刚体"（PBF/FLIP 的粒子↔刚体碰撞走同一套边界粒子口径）——待定。

### 9.3 两个测量坑（已修，写下来省下一次）

1. **`queue.submit` 是异步的**：只给它计时会把**入队**当执行（实测 125k 竟"快"于 64k）⇒
   必须让"**提交 + 同步读回**"一起计时；本探针已改（`per_dispatch_ms` = reps 轮 + 一次回读的均值）。
2. **一次性 setup 与稳态必须分开报**（0.46 s 的设备/编译不能混进每轮成本）。

### 9.5 第二片（2026-09-23）：**力+黏度相位**也上 GPU ⇒ 两相位同档对拍（§9.4 ② 已完成）

**已落地**：`force.wgsl`（与 CPU `force_pass` **同式、同遍历序**；点积手写展开，避开 WGSL `dot`
未规定的归约序）+ 探针改成**一次 setup 跑两核**（共享输入缓冲、同一个提交里"先密度后力"）⇒
GPU 侧有了完整的"流体两相位"。对拍仍用**示例内 CPU 参考实现**（与 GPU 同输入/同式/同序，
不是引擎 `step()` 之后的 `densities()`——那是拿积分前的位置比积分后的位置，首片踩过）。

**新踩的两个坑（写下来省下一次）**：

1. **wgpu 要求 storage 绑定的访问权限精确匹配**：`Storage { access: LOAD }` 与 `LOAD | STORE`
   不等价（实跑 validation error）⇒"密度核写 `dens` / 力核只读 `dens`"**不能共用一张 bind group
   layout**。改为**每核一张布局 + 各一个 bind group**（仍全在一次性 setup 内，不进稳态计时）。
2. **uniform 缓冲里 `vec3` 按 16 字节对齐**：Rust 侧 `#[repr(C)]` 结构体若直接放 `[f32; 3]`，
   字段会错位到 44 字节处（WGSL 要 48）⇒ 必须在 `gvec` 前显式补 4 字节 `_pad0`。这类错位只会
   表现为"数值全错"而非报错，**对拍前先核布局**。

| 判据 | 64k 粒（40³） | 125k 粒（50³） | **301k 粒（67³）** |
|---|---|---|---|
| 密度：最大绝对差（逐位相同） | 3.66e-4 kg/m³（52.3%） | 4.27e-4 kg/m³（54.1%） | 4.27e-4 kg/m³（**65.0%**） |
| 加速度：最大绝对差（逐位相同） | 9.54e-7 m/s²（38.1%） | 9.54e-7 m/s²（37.9%） | 1.91e-6 m/s²（36.7%） |

### 9.6 口径 A 的三次尝试（2026-09-23）：**本栈上不可达** ⇒ 转口径 B 并定容差表（§9.4 ④ 已完成）

| 尝试 | 做法 | 结果 |
|---|---|---|
| ① `precise` | WGSL 的精确浮点限定符（禁 FMA 收缩） | **naga 27 前端没有这个关键字**（`precise let x = …` 报 `expected assignment`）⇒ 语法层就不可用 |
| ② bitcast 屏障 | 每个乘积经 `bitcast<u32>` 双跳"物化"，挡收缩 | **逐位率一字不变**（52.26% / 最大 ulp 6 原样）⇒ 被优化器折掉，无效 |
| ③ 显式 fma 对照 | 让 CPU 参考用 `mul_add` **模拟 GPU 的收缩**（判定性实验） | >2ulp 的粒 **2465 → 1437（-42%）**，但**最大 ulp 仍是 6** ⇒ 收缩是主因之一 |

**关键判读**：残差最大只有 **6–7 ulp**（64k 档 6 / 301k 档 7；>2ulp 的粒占 2–4%），
而**一个邻居项约值 3e5 ulp** ⇒ 若邻域集/遍历序真有差，ulp 差会是六位数。
**⇒ 结构性一致（同式、同序遍历、同邻域集）已经成立，残差纯粹是"收缩/舍入"噪声。**
naga 没有 SPIR-V `NoContraction` 的出口，wgpu 也不给"注入装饰"的手段 ⇒ **口径 A 在此栈上到此为止**，
按骨架口径走 **B（量化哈希 + 容差）**。

⚠️ **ulp 指标的适用面**：`acc`/`xsph` 的最大 ulp 数字会爆到 1e8——那是**近零分量**（分量本身
趋 0 ⇒ ulp 趋 0）造成的假象 ⇒ **密度用 ulp 判读，`acc`/`xsph` 一律用绝对残差判读**。

**容差表（口径 B 用；取实测最大残差再留 1 个数量级余量）**：

| 量 | 实测最大残差（301k 档） | 建议容差 |
|---|---|---|
| 密度 | 4.3e-4 kg/m³（相对 4e-7，最大 7 ulp） | 相对 **1e-5** |
| 加速度 | 1.9e-6 m/s²（对 g≈10 ⇒ 相对 2e-7） | 绝对 **1e-4 m/s²** |
| XSPH 增量 | 1.5e-11 m/s | 绝对 **1e-9 m/s** |

（容差只用于**跨 CPU/GPU 对拍**；CPU 侧自己的串行 vs 并行**逐位门不动**。）
探针示例已内置 **ulp 诊断**（最大 ulp 差 + >2ulp 计数）——只报"最大绝对差"会让人误判成结构性问题。

## 10. 网格重建上卡（§9.4 ①/③）：**先算账**（2026-09-23）

**CPU 现算法**（`vxl-phys-fluid::UniformGrid::rebuild`）：两遍扫计数排序——
① 逐粒 `bin_index_of` 计数；② 前缀和；③ **按粒子索引升序**用 `counts[c]` 当游标写 `items`
⇒ **格内序 = 索引升序**（这正是"与 CPU 逐位同表"的前提）。

**关键结论**：GPU 要与 CPU 同表、**或哪怕只是"逐轮可复现"**，就必须做**确定性并行计数排序**。
原子占位（`atomicAdd` 抢槽）虽然最便宜，但同一输入在不同轮次会给出**不同的格内序** ⇒ 逐轮哈希漂移
⇒ 破坏本仓"同输入 ⇒ 同哈希"的可复现契约 ⇒ **不可用（这不是精度问题，是契约问题）**。

| 候选 | 成本 | 内存 | 判定 |
|---|---|---|---|
| **LSD 基数排序**（按 bin，8 位数字；B ≤ 2²⁰ ⇒ 3 趟） | O(n·趟数)；每趟 = 直方图 + 扫描 + **稳定**散列 | 每趟 2×n + (wg×2⁸) 计数矩阵 | ✅ **与 CPU 同表**（稳定性 = 索引升序），且是 PBF/FLIP 按格/哈希排序的**同一原语** |
| 分块 rank（chunk×bin 计数矩阵 + 块内 O(L) rank） | O(n·L) 比较 | (n/L)·B·4 B：L=1024、n=10⁷、B=2²⁰ ⇒ **≈40 GB** ❌ | 同表但**不可扩** |
| 原子占位 | 最便宜 | 无 | 逐轮不可复现 ❌ |
| 留 CPU（现状） | 8 线程 / 300k 档 **23.3 ms/tick**（占 tick 18%） | — | 见下"混合口径" |

**决定**：~~走 LSD 基数排序~~ ⇒ **同日落地时改选**（见 §11）：**原子占位 + 逐格按索引规范化**——
它同样给出"与 CPU 逐位同表"，实现量小得多、300k 档只要 0.4 ms。**基数排序降级为退路**：
当"格内元素数无界"时（`cap` 护栏报 `overflow > 0`）才需要它。原账保留在上表，理由不删——
它记录了"为什么一开始会以为非排序不可"（漏掉了"原子乱序可以被**规范化**掉"这一步）。
在它落地前，"GPU 流体"的诚实口径是**混合管线**——估算（**未实测**，按已测分量相加）：

| 配置（300k 档、4 子步） | 每 tick | 对纯 CPU 128.2 ms |
|---|---|---|
| 纯 CPU（8 线程，现状） | 128.2 ms | 1× |
| **混合：CPU 网格 + GPU 两相位**（不含传输） | 23.3 + 4×1.27 ≈ **28.4 ms** | **≈4.5×** |
| 混合（含上传/回读：8.4 MB 上传 + 4.8 MB 回读 / 子步，按 PCIe ≈10 GB/s 估） | ≈ **33.6 ms** | ≈3.8× |
| 全 GPU（网格上卡后，网格 ≈1 ms） | ≈ 1 + 4×(1.27 + 1.3) ≈ **11.3 ms** | ≈11× |

⇒ **传输是第二根杠杆**（要与 §9.4 ③ 的"常驻缓冲 + 少回读"一起做）：纯相位 5.35 ms/tick 很好听，
但每子步 13 MB 的 PCIe 往返会把它吃掉一半以上。**下一步先做网格上卡 + 常驻缓冲，再报整 tick 数字。**

## 11. 网格重建上卡：**逐位同表**已达成（2026-09-23，§9.4 ① 完成）

**落地**：`src/grid.wgsl`（四入口）+ `src/grid.rs`（宿主）+ `examples/gpu_grid_probe`（对拍）。
四步与 CPU `UniformGrid::rebuild` 一一对应：

| 入口 | 做什么 | 与 CPU 的关系 |
|---|---|---|
| `bin_count` | `bin = min(clamp(floor((p−min)·inv)), total−1)`；`counts[bin+1] += 1` | 分箱**逐位一致**（只有"一次减、一次乘、一次 floor"⇒ 没有可收缩的 `a*b+c`）；原子加的**值是精确整数**、与顺序无关 |
| `scan` | `counts` → `start`：**含尾**前缀和（单工作组、分块 Hill-Steele） | 语义要与 CPU 对齐（⚠️ 见"踩的坑"） |
| `place` | `cursor`（= `start` 副本）上 `atomicAdd` 取槽 ⇒ `items[slot] = i` | 槽位**不定序**（要被下一步规范化掉） |
| `canon` | 逐格把 `items` 段**按粒子索引升序**插入排序 | **= CPU 的格内索引升序**；结果与原子顺序**无关** ⇒ 逐轮可复现 |

**护栏**：`cap` 卡住段长（超限则不规范化 + `overflow += 1`）；**判据是 `overflow == 0`**，
非 0 ⇒ 表不再与 CPU 同表（engine 侧可拿它当"回退 CPU 网格"的开关）。

**踩的坑（值得复用定位法）**：`start` 的语义差一个格桶——CPU 把"格 c 的计数"写在 `counts[c+1]`，
所以 CPU 的 `start[k]` 是 `counts` 的**含尾**前缀和；我第一版写成**独占**前缀 ⇒ `start[1]` 给成
`counts[0]`=0（CPU 给 8）⇒ **表整片错位却"形似"**（每格集合仍对、逐粒 bin 仍全对，只有 start/items 全错）。
定位两步：① 核里先写**可辨认哑值**（`start[idx] = idx*3+7`）⇒ 一眼分清"写通路坏了"还是"算错了"；
② 诊断槽一次回读 `total/chunks/counts[1]/s_scan[255]/running` ⇒ 立刻看出前缀和算对了、只是语义错位。

**读数（三档全部与 CPU **逐位全等**，`overflow == 0`）**：

| 档 | GPU/轮（四入口 + 清零 + 拷贝 + 同步回读） | CPU/子步（`phase_us()[0]`÷4，threads=1） | 比值 |
|---|---|---|---|
| 64k | 0.143 ms | 1.061 ms | 7.4× |
| 125k | 0.204 ms | 2.447 ms | 12.0× |
| 301k | **0.399 ms** | 5.763 ms | **14.4×** |

- **逐位同表**：`start` / `items` / 逐粒 bin 三样全等（三档都是 0 项不同）；表哈希 CPU ≡ GPU
  （125k 档 `0xb895c37c2fd663fb`），**连跑两遍哈希不变** ⇒ 原子占位的不定序确实被 `canon` 规范掉了。
- **CPU 网格相位其实不并行**（301k：8 线程 23.30 ms/tick vs 1 线程 23.05 ms/tick）⇒ 这 14× 是对着
  引擎**最快的 CPU 路径**拿的，不是对着串行基线。
- ⚠️ **规模上限**：单维分派上限 65535 个工作组 ⇒ 当前 `n ≤ 4.19M`（`groups_n = n/64`）；
  再大需二维分派（与 10M 档一起办）。

**端到端口径更新**（估算，按已测分量相加；301k、4 子步）：CPU 网格 23.3 ms/tick → **GPU ≈1.6 ms/tick**
⇒ 整 tick ≈ 1.6 + 4×1.27 = **≈6.7 ms** vs 纯 CPU 128.2 ms ⇒ **≈19×**（不含 PCIe 往返；含往返按 §10
的估法 ≈11×）⇒ §9.4 ③ 只剩"常驻缓冲 + 少回读"与 EOS 上卡。

## 12. 常驻缓冲的**整 tick 管线**（2026-09-23，§9.4 ③ 主体完成）

**落地**：`eos.wgsl` + `integrate.wgsl` + `src/pipeline.rs`（`Packet`：8 条管线 / 5 张绑定布局 / 5 个
bind group，缓冲**只建一次**）+ `examples/gpu_tick_probe`（整 tick 计时 + 与 CPU 引擎的**逐 tick 漂移表**）。

一条命令链 = `分箱 → 扫描/占位 → 规范化 → 密度 → EOS → 力 → 积分`，每 tick `substeps` 次；
**每 tick 只回读一次**（真要耦合才回读）。

### 12.1 读数（零重力 + 剪切初速：动力学充分、又留在箱内）

| 档 | CPU 引擎（相位合计） | **GPU 常驻** | 加速比 | 含耦合回读 | 加速比 |
|---|---|---|---|---|---|
| 125k | 324.47 ms/tick | **5.76 ms/tick**（3 次 [6.86, 5.76, 5.78] 取最小） | **56.3×** | 6.75 ms（+0.99 回读） | 48.1× |
| 301k | 770.83 ms/tick | **9.36 ms/tick**（3 次 [9.86, 9.36, 9.88]） | **82.3×** | 11.95 ms（+2.59 回读） | 64.5× |

（CPU 侧逐次波动 ±2%：125k 档复跑得 317.5 ms/tick、GPU 5.68 ms/tick ⇒ 55.9×；量级结论不受影响。）

**逐 tick 漂移表**（同一初态、CPU/GPU 各推一步再比）：40 tick 后 `|Δpos|max ≤ 1e-5 m`（= 晶格间距的
0.02%）、`|Δv|max ≤ 1e-4 m/s`、**动能比 1.0000**、NaN 0、`overflow` 0 ⇒ **口径 B 的轨迹口径在端到端成立**
（本场景里 GPU 几乎复刻引擎轨迹；判读口诀：**max ≡ mean ⇒ 刚性平移 ⇒ 一定是接线/口径错，不是混沌**）。

**相位消融**（2 次取最小，指示性）：分箱 0.11 → 扫描/占位 0.45 → 规范化 0.81 → 密度 1.90 → EOS 1.98
（+0.08，近乎免费）→ 力 3.79 → 全链 6.73（125k 档）。⇒ **网格只占整 tick ≈12%**，开销回到浮点相位
（内存受限的邻域遍历）⇒ 下一步的杠杆是**减少候选/提高局部性**，而不是再加相位。

### 12.2 三条测量教训（都踩过，写下来）

1. **计时前必须冻结状态**：消融计时逐项推进流体，剪切把粒子压实 ⇒ 邻域候选变多 ⇒ 后面的项天然更慢。
   实测把"规范化"从 0.36 ms 虚报成 **7.09 ms/tick（20×）**。修法：`Packet::snapshot/restore`，
   每次计时前还原到同一状态。
2. **`run` 里不许藏"预热"**：我给 `Packet::run` 内嵌了"预热一个 tick"，于是每次调用都**多推进一 tick**
   ⇒ 漂移表呈现"整块刚性位移 + Δv 恰好 = g·dt"，看着像接线错、又像混沌，实际是被测对象被提前推进。
   修法：预热由调用方显式做一次**丢弃计时**的 `run`。
3. **短窗受 GPU 时钟爬升支配**：同配置 100 tick 内能差 2×（4.45 → 8.05 ms/tick）⇒ **3 次 × 100 tick 取最小**
   并打印原值（离散度可见），别拿单次短窗当读数。

### 12.3 与 CPU 引擎的**已知差距**（下轮）

- **包围盒**：本片箱子**固定**（不重算）。真后端要每 tick 从位置做 min/max 归约 + 同一套"`h` 起、
  超预算翻倍"规则算 `dims/inv`（一个 reduce 核 + 一个单线程 setup 核）。**边界钳位不破坏邻域正确性**
  （钳进边缘格的粒子仍被 `r ≤ h` 刷掉），但会让边缘格变挤、变慢 ⇒ 自由落体场景几十 tick 后计时失真
  （实测 3 ms → 10 ms 量级），所以本片选了"零重力 + 剪切"这种留在箱内的场景。
- **边界/提供者相位**：2b 的边界粒子（`pmass`、反作用）与壁面/provider 分支本片未接；
  `integrate.wgsl` 也只做流体前缀（本片全是流体）。
- **分派上限**：单维 ≤65535 工作组 ⇒ 当前 `n ≤ 4.19M`；10M 档要二维分派。
- **传输**：耦合回读已实测（125k 0.99 ms / 301k 2.59 ms）——它现在是"第二根杠杆"里的**小头**
  （因为每 tick 只回读一次），大头是**上传**（本片常驻 ⇒ 零上传）。

## 12.4 每子步包围盒（2026-09-24，§12.3 第一条**已闭合**）

**口径**：CPU 引擎在 `substep()` 开头就 `UniformGrid::rebuild(&pos, h)` ⇒ **每子步**一次；GPU 必须同频。

**实现**（三片，各自可验）：
1. `vxl_phys_core::grid::grid_box` —— 箱子规则**单一来源**（`bin` 从 `h` 起、`dims = floor(ext/bin)+1`
   钳 16384、总格数超预算翻倍；`GRID_MAX_BINS` 与 `GRID_DIM_MAX` 随之上移）。CPU 侧 `rebuild` 改调它，
   fluid 侧一条测试锁"两侧逐位相同"。
2. `bbox.wgsl` + `bbox.rs` —— 归约核：f32 → **单调 u32 有序映射** + `atomicMin/Max`（min/max 是精确运算、
   与求值顺序无关 ⇒ 原子不破坏确定性）。三件套仍在主机侧按 `grid_box` 算（"规则只有一处"）。
   上卡对拍 3 例（本机 RTX 4060 Ti）：n=3/64/65/1000 手算期望 + 5000 粒全量，`min/max/bin/dims/inv`
   **逐位相同**。
3. `Packet`：`PacketCfg::{recompute_box, grid_bins_cap}` + `Packet::refresh_box`（归约 → 回读 24 B →
   `grid_box` → 写两组 uniform 的动态字段）；`run_stages` 在开关打开时按子步提交，成本记进
   `TickMs::box_ms`。`gpu_tick_probe` 加 `--box=follow` / `--gravity`。

**读数**（40³ = 64000 粒、300 tick、自由落体 0.981 m/s²）：

| 档 | 整 tick | overflow | Δpos(t=300) | \|Δv\|max |
|---|---|---|---|---|
| 固定箱子（§12.1 口径） | 65.1 ms/tick（2.1×） | **20 ⚠️** | 0.00010 m | 2e-5 |
| `--box=follow`（主机侧规则 + 每子步 24 B 回读） | 3.57 ms/tick（42.1×） | **0 ✅** | 0.00010 m | 2e-5 |
| `--box=follow`（**卡上 setup**，零回读） | **≈2.9 ms/tick（51.9×，150 tick 档）** | **0 ✅** | 0.00003 m | 1e-5 |

⇒ 收益是**性能（对固定箱子 ≈25×）与护栏清零**；本场景里固定箱子并未让物理变错（大箱子给出同样的
邻居集合，只是慢且挤）。**接线时踩的三条**（都已修）：① 扫描→占位的拷贝长度按 `self.total` 算 ⇒
箱子跟随后活的格数变了、长度不符 ⇒ 游标错位、力爆炸（判别法：**零重力下也炸 ⇒ 必是接线 bug**）；
② 格表缓冲不会自增长（CPU 侧 `Vec` 会）⇒ 需要 `grid_bins_cap` 显式给额度；③ **`o2f` 的分支顺序写反**
（有序值高位为 1 的那一半来自**正**数）⇒ setup 核解出的角点全乱（y 解成 -45..29）、**而归约一直是对的**
——症状出现在"消费方解码"而不是"归约"；修好后卡上 dims/total **逐位**与主机相同（测试钉住）。

### 12.5 卡上 setup（2026-09-24，§12.4 的开口项**已闭合**）

**做法**：`bbox.wgsl` 的 `box_setup`（单线程）把 `(lo,hi)` 算成与 uniform 动态字段**同形**的
`box_out`（`[min.xyz, inv, dims.xyz, total]`，后四槽是 u32 位模式）；`Packet::refresh_box` 用
**设备内 `copy_buffer_to_buffer`** 把它搬进两组 uniform —— **全程零回读**。配套两件：
① `scan` **一次写 start 与 cursor 两份**（省掉每子步按分配额度拷 4 MB 的 `copy_buffer_to_buffer`）；
② `box_setup` 的翻倍循环加**硬上限**（extent 逆天真时不会把 GPU 转死——实测挂过一次）。

**成本记账**（`TickMs::box_ms`，探针会打印）：主机侧规则那条路 **2.77 ms/tick（占整 tick 88%）** ⇒
卡上 setup **0.27 ms/tick（10%）**。**这条才是"跟箱子"的主杠杆**（不是箱子紧本身）。

**仍未做**：边界/提供者相位；`integrate.wgsl` 的刚体前缀。

**GPU 用例必须串行（实测，已加锁）**：同一块卡上**并发**跑"建缓冲 + 提交 + 回读"会**挂死**
（挂住的那个进程还占着 `vxl_phys_gpu-*.exe` ⇒ 后续链接期 `Permission denied`）。`cargo test` 默认
多线程跑测试 ⇒ 已用一把进程内互斥锁把 GPU 用例串行化（`bbox.rs` 的 tests 模块），否则会偶发挂住
整轮测试、连带门链与 CI；无适配器的机器上用例会快速跳过，锁不造成等待。

## 13. 边界/提供者相位（2026-09-24，第一条腿落地）

**核侧其实已经是一半通的**（读码核对）：`density.wgsl` 有 `sum_b = Σ pmass_j·W`（边界粒子的密度贡献）、
`force.wgsl` 的邻居项用 `m_j = pmass[j]` —— 也就是 2b 边界粒子的**数学已经在里面**了。

**CPU 侧语义（对齐口径，逐条对应）**：网格/密度/压力/力跑**全部**粒子（邻域必须看得见边界粒子），
**积分（含 XSPH/CFL）只跑 `0..n_fluid`**（边界粒子运动学冻结）；`boundary_pass` 是**提供者（体素/三角网/
喷溅）壁面**的投影——**边界粒子 tank 不需要它**（体↔流体耦合走壁压 `sum_b` 自平衡）。

**本轮落地**：
- `PacketCfg::n_fluid` + `Packet.groups_fluid`：积分分派只覆盖流体前缀（此前按 `n/64` 全跑 ⇒
  边界粒子会被积分、飘走）。纯流体场景 `n_fluid == n` ⇒ **与旧口径逐位一致**（已用漂移表回归）。
- `FluidSystem::raw_particles() -> (pos, vel, pmass, n_fluid)`：后端/耦合用的**全粒子**视图
  （`positions()`/`velocities()` 只给流体前缀，是给渲染/导出的）。

**剩下**：① **反作用回读**（2b 的 `bforce` → 体上的力/力矩，`aggregate_reactions` 现在只在 CPU 侧；
`force.wgsl` 仍只算流体前缀的力）；② 提供者壁面的 SDF 分支（含密度轮的"壁面镜像鬼影"——CPU 侧
`wall_planes` 那条，走 provider 几何，**边界粒子 tank 用不到**）；③ `integrate.wgsl` 的刚体前缀。

### 13.1 边界粒子 tank 的验收（2026-09-24）——**已对齐**

`gpu_tick_probe --tank`：静态盒体（地板 + 四壁）经 `set_boundary_particles` 变成 2b 边界粒子，
**全部粒子 + 逐粒 `pmass`** 上传（`FluidSystem::raw_particles()`），CPU/GPU 同场景跑逐 tick 漂移表。
场景：24³ 流体（13824）+ **20864 边界粒子**，零重力 + 剪切初速。

| tick | Δpos max | \|Δv\| max | 动能比 | NaN |
|---|---|---|---|---|
| 1 | 0.00000 m | 1e-5 m/s | 1.0000 | 0 |
| 30 | 0.00001 m | 4e-5 m/s | 1.0000 | 0 |
| 60 | **0.00004 m** | 1.8e-4 m/s | **1.0000** | **0** |

**接线里抓到的两条**（都是"数学早就在、接线没接"）：
1. **相位 uniform 的 `n_fluid` 槽位写的是总粒子数**：`density.wgsl`/`force.wgsl` 靠 `j < n_fluid` 区分
   "流体邻居 ⇒ 计 `sum`"与"边界邻居 ⇒ 计 `sum_b`"⇒ 写错后**全部邻居都当流体** ⇒ 一 tick 就炸
   （动能比 289）。修：`make_params` 写 `cfg.n_fluid`。
2. **密度核开头 `if i >= n_fluid { return; }`**：GPU 从不给**边界粒子**算密度 ⇒ 力核的
   `press[j]/(ρ_j²)` 读到 0/0 ⇒ **8798 粒 NaN**。修：密度核处理**全部**粒子，边界走 Akinci 口径
   （自身项用自己的 `pmass`、**不吃边界-边界对**、流体项**逐项** `pmass[j]*w`）——与 CPU
   `fluid_density.rs` 的边界分支逐条对应。相位 uniform 为此补了 `n_total` 槽（原 `_pad`）。

代价与注意：密度核多累一个 `sum_bf`（流体场景也跑，约几 %）；`force.wgsl` 仍只算流体前缀（反应未接）。

### 13.2 反作用回读（2026-09-24：**力已上卡并验收**）

**CPU 侧口径（读码核对，`fluid_force.rs`）**：主循环 `for i in 0..nf`（**流体** i），邻居循环里
`if j >= nf` 时累到**边界粒子**上：`bforce[j] -= d·(mi·(coef + cv)/denom)`，其中
`d = p_i − p_j`（i 流体、j 边界）、`coef = mj·(ks·t²)·(ci² + cj²)`、`cv` 是 Monaghan 黏度项；`bforce`
每子步**清零重累**，再由 `aggregate_reactions` 按 `spans` 聚合 → `breact`。

**GPU 侧落地（`force.wgsl`）**：守卫改 `i >= P.n_total`，分两支——流体支 = 加速度 + XSPH（现状），
边界支 = **反作用 gather**：只吃流体邻居、成对质量因子取 `m_i`（于是 `m_i·m_j·…`，与 CPU 的
`mi·coef` **同式**）、符号**自动落回 `+d`**（核里的 `d = p_i − p_j` 与 CPU 的 `d = p_流体 − p_边界`
反向 ⇒ 两处符号都翻）。**流体支因 `mfac = 1.0` 而逐位不变**（乘 1.0 精确）⇒ 纯流体场景零影响。
回读：`Packet::read_boundary_forces(n_fluid)` 只回读 `out_b` 的**边界段**（非全量）。

**验收（`gpu_tick_probe --tank`，20³ 流体 8000 + 16000 边界，20 tick）**：
`max |ΔF| = 1.057e-4 N`（相对 `Σ|F_cpu|` = **6.70e-7** ⇒ 只剩浮点累加序，与口径 B 同源）；
`ΣF`：CPU `1.3609e1` vs GPU `1.3608e1` N（差 `1.35e-3` N）；NaN 0、overflow 0。
CPU 侧的可比对象先钉住：`tests/boundary_reaction_balance.rs`（成对力等大反向，残差相对 **1.36e-7**）+
访问器 `FluidSystem::accelerations()` / `boundary_forces()`。

**还剩半步**：~~把逐粒反作用**按 `spans` 聚合成每体 `(F, τ)`**（= `breact` 的 GPU 侧）~~
——**已落地，见 §13.3**；**仍剩**：接进 facade 的耦合回路（边界粒子每 tick 随体姿态重建 ⇒
需要每 tick 上传边界段：20k 粒 × 12 B ≈ 240 KB/tick）。`Packet::read_boundary_forces` 给出最小回读形态。

**三条已认下的判据**（实现前先认，省得来回）：① 成对力**对称**（两边都是乘积 `m_i·m_j`，`μ` 换参照系
时两因子同时变号 ⇒ 同值）⇒ 边界侧可以用 gather 写；② **遍历序不同 ⇒ 只能到口径 B**（CPU 按流体
索引序、GPU 按邻居表序；要逐位就得上"按索引序的散射"，而那需要原子浮点加 ⇒ 反而**不定序** ⇒ 更差）；
③ 回读量：只回读边界段（或更好：聚合后的每体 6 个 float）。

### 13.3 反作用的**卡上聚合**（2026-09-24，§13.2 的"剩半步"落地）

**做了什么**：把 CPU `aggregate_reactions` 那一步搬到卡上——新核 `src/reduce.wgsl` +
`pipeline/reaction.rs`（`ReactionStage`）。逐粒反作用 → 每体 `(F, τ)`，回读量从"边界段"
（16k 粒 × 24 B = **384 KB/tick**）降到**每体 6 个 f32**（5 体 = **120 B/tick**）。

**设计（三条都写在代码里）**：
- **求和序**：一个体 = 一个 workgroup，段内**升序串行**累加 ⇒ 与 CPU 的 `for k in start..end`
  逐条对应；**不用原子加**（原子浮点加不定序 ⇒ 比口径 B 更差，判据②）。
- **参照系/符号**：核里 `d = p_k − origin`、`τ = Σ d × f_k`，按 `Vec3::cross` 的**展开同序**写
  （不用 `cross()`/`dot()` 内建：归约序未规定——密度核同款注意）。
- **段表即接口**：上传 `(体原点, start, end)`（32 B/体），长度由缓冲字节数给出（`arrayLength`）
  ⇒ 不需要额外 uniform；体 id 只留在主机侧做还原，返回序 = 段序（与 `boundary_reactions()` 同序）。

**验收（`gpu_tick_probe --tank`：20³ 流体 8000 + 边界 16000、20 tick）**：

| 读数 | 值 | 相对量 |
|---|---|---|
| 逐粒 max \|ΔF\|（**回归**：接线未动逐粒口径） | 1.057e-4 N | 6.70e-7（对 Σ\|F_cpu\|） |
| **每体 max \|ΔF\|**（5 体聚合） | **1.306e-3 N** | **9.13e-6** |
| **每体 max \|Δτ\|** | **4.420e-4** | **2.23e-5**（对 Σ\|τ_cpu\|） |
| 自洽：Σ_体 F_gpu − Σ_粒 F_gpu | 3.195e-5 N | 同一批项换序求和 ⇒ 只该差舍入 |

**判据**：每体相对量落在 **1e-5 量级**即通过——它**同源于逐粒的口径 B**：逐粒差 ≤ 1.06e-4 是浮点
累加序，一个壁 3200 粒 ⇒ 随机游走累积 ~√N·1e-5 ≈ 5e-4，实测最大 1.3e-3 正是该量级
（5 个体取最大）。**判读法同 §12.2**：**线性增长才是接线错**，随机游走是口径 B 的必然。
⇒ 反作用这条链（2b 边界粒子 → 卡上力 → 回读 → 聚合）**端到端对齐**，`(F, τ)` 的量纲
= **力**（与 CPU `breact` 同口径），可直接喂耦合回路。

**顺带的 CPU 侧两处**（都是**上帝对象门**的账）：新增只读访问器 `FluidSystem::boundary_spans()`
（段表 = GPU 聚合的输入；落点 `fluid_boundary.rs`），并把 `boundary_pass` 的"同位坍缩消解"抽成
`separate_coincident`（**纯搬移**，语义未改）——后者让该档最长函数 **79 → 57 行**，于是文件涨
12 行走"净账为负"通道合法放行（门逐条打印，见 `god_gate.py`）。

**后续**：**耦合回路**（§13.5）已落地协议与验收（每 tick 重建边界段 + 只上传边界段 + 卡上聚合）；
**仍剩 facade 接线**——把这条链接进 `vxl-phys::World` 的流体后端（`fluid_reaction_pass` 施加 `(F, τ)`）。

### 13.5 耦合回路：每 tick 重建边界段 + 卡上聚合（2026-09-24）

**协议（三条腿齐了）**——每 tick：
1. **宿主重建**：按体姿态重建边界粒子（CPU `set_boundary_particles`：位置 = 刚性变换、
   速度 = 体面速度 `v + ω×r`）；
2. **只上传边界段**：`Packet::upload_boundary_segment(n_fluid, &pos[n_fluid..], &vel[n_fluid..])`
   ——流体状态留在卡上（回读再写回等于白送一次往返，§12 的账）；`pmass` 不动（形状与间距不变
   时是常量）；段表由 `aggregate` 每次带上 ⇒ **体原点随体走**，力矩参照系自动跟上；
3. **两侧各推进一个 tick**；4. `ReactionStage::aggregate` → 每体 `(F, τ)`（facade 要施加的量）。
   上传量 = 每粒 24 B（pos+vel）：16k 粒 = **384 KB/tick**；回读仍是每体 6 个 f32（**120 B/tick**）。

**新 API 的一条纪律**：`upload_boundary_segment` 长度不符**直接报错**（不静默截断）——写半段会让
一部分边界粒子停在上一 tick 的姿态，那是**静默的物理错**，比 panic 难查得多。

**验收（新探针 `gpu_coupling_probe`：20³ 流体 8000 + 边界 16000、地板 A = 0.02 m / f = 1.5 Hz、
240 tick × 4 子步；**关 XSPH** 让动量账干净）**

| 判据 | 读数 |
|---|---|
| **第 1 个 tick 的逐体相对差**（接线错的探测器） | relF **3.10e-6** / relT 3.98e-6 |
| 逐 tick 最坏相对差（整段 240 tick） | relF 1.05e-4 / relT 4.41e-4 |
| 动量账**两侧之差**（`Σ_体∫F dt` vs `−ΔP_流体`） | **4.91e-6** |
| 非有限速度 | **0** 粒 |
| 时间序列 | 漂移 0 → 0.00216 m；relF 稳在 1e-5…1e-4，**不随漂移长** |

**两个"看着像错、其实不是"的判读（写下来免得下一轮重查）**：
1. **绝对动量账残差 54%**：逐 tick 拿的是**末子步**的力（CPU/GPU 都只给末子步），而一 tick 有
   4 个子步 ⇒ 采样项 O(`dt`·dF/dt)。边界在动时力是尖的（每 tick 地板走 0.16 晶格间距 ⇒ 冲量式
   驱动），单点采样与 tick 均值能差几十个百分点，240 tick 累积成随机游走。**两侧之差没有这一项**
   （同一采样）⇒ 它才是锋利的判据；绝对值只当量级看。
2. **静态对照（`--amp=0`）的 relF 在 t≈200 后跳到 4e-3**：它与漂移同步（0.003 → 0.005 m ≈ 10%
   晶格间距 ⇒ 邻居集合开始不同）⇒ 这是**口径 B 混沌**。判据是 **t=1 就大才是接线错**（实测
   1.75e-6 ✓）。

**守卫（两条，都是 diff 空）**：
- **重传 A/B**（`--amp=0` vs `--amp=0 --no-reup`）：静态下"每 tick 重传"与"不重传"**逐位相同**
  ⇒ 重传路径零副作用。
- **确定性**：同配置连跑两次逐字相同（含每 tick 的回读聚合）。
- ⚠️ **曾想用的"tank 探针 240 tick"对照不能用**：它与本探针在 **XSPH 开关**与**箱子口径**
  （固定 vs 每子步重算）上都不同 ⇒ 混了两个变量（23× 的漂移差全来自这两项）⇒ 改用上面的自 A/B。

**仍未做（下一轮）**：接进 `vxl-phys::World` 的流体后端——facade 侧把"体姿态 → 重建 → 上传 →
聚合 `(F, τ)` → `fluid_reaction_pass` 施加"串起来（量纲 = 力，与 CPU `breact` 同口径）；
再往后才是提供者壁面 SDF 分支与 `integrate.wgsl` 刚体前缀。

### 13.6 闭环：GPU 的反作用**推得动刚体**（2026-09-24）

**与 §13.5 的分工**：§13.5 的体是**脚本驱动**的（只验"力算得对不对"）；本节是**闭环**——
反作用 → 体运动 → 新姿态 → 重建边界粒子 → 再算力。两条链（CPU 引擎 / GPU 卡上）各跑一条闭环对拍。

**探针** `gpu_body_probe`（**开放域、无箱壁** ⇒"流体 + 挡板"是**闭合系统**，动量账没有第三方向量）：
12³ 流体块带 +x 初速 0.8 m/s；前方 0.35 m 一块**挡板**（0.25×0.4×0.4 m、4000 kg/m³ ⇒ 160 kg；
厚度 **2.5h** ⇒ 避开"体薄于 2h 反作用失准"）；零重力、关 XSPH；体只解平动（转动锁死，力矩仍逐 tick 对拍）。

| 判据 | 读数（240 tick） |
|---|---|
| 体末速 `vx`（CPU vs GPU） | 0.28610 vs 0.28610（**相对差 1.98e-5**） |
| 体位移（t=240） | 1.74588 vs 1.74587 m（差 **7.6e-6 m**） |
| 动量账**两链之差** | **1.98e-5**（相对体冲量 46.2 N·s） |
| 逐 tick 反作用相对差（逐粒最大 / Σ\|F\|） | t=40 **7.9e-5** → t=240 **1.8e-2**（随漂移长） |
| 非有限速度 | **0** |

**三条判读（写下来免得重查）**：
1. **"逐粒力的相对差"与"体级轨迹"不是一回事**：晚期逐粒差涨到 2e-2（邻居集合已不同 ⇒ 单粒力可翻转），
   而**合力**仍对到 2e-5 ⇒ 驱动体的是合力。**别拿逐粒差当验收尺**。
2. **绝对动量账残差 29%**：同 §13.5 的**末子步采样**项（逐 tick 只拿得到末子步的力，而流体动量之变是
   **全部子步**积出来的；撞击段力是尖的）⇒ 锋利的是**两链之差**（同一采样，相减抵消）。
3. **空载 tick 必须剔除**：撞击前/推走后 `Σ|F|` 只有浮点噪声，比值没有意义（首版把撞击前的噪声
   记成"12% 的最大相对差"）⇒ 探针按 `LOAD_MIN` 标"空载"并只统计有载 tick。

**与 facade 的对应**：`World::fluid_pass` 的时序就是本探针的时序（先按新姿态重建边界粒子、再步进；
反作用在体子步里由 `fluid_reaction_pass` 施加）⇒ **接缝以下全部就绪**。

### 13.7 下一步：facade 接线（**尚未做**）——门槛不在步进，在两处主机侧依赖

读码核对（`world_struct.rs` / `world_step.rs`）后要认下两条**真门槛**：
1. **2a 介质采样**：`World::medium_pass` 每 tick 对流体做 `sys.sample(p)`（浮力/阻力）——GPU 档一旦把
   流体状态搬上卡，这条要么每 tick 回读（8k 粒 ≈ 96 KB/tick 尚可；30 万粒 ≈ 3.6 MB/tick ✗），
   要么把采样也上卡。**但纯 2b 场景不需要它**（被 2b 覆盖的体由 2b 接管 ⇒ 那段采样短路）。
2. **近域过滤要流体的 AABB**：`refresh_fluid_boundary` 用 `particle_bounds(&fluids[fi])` 决定"哪些体
   进边界粒子集"——主机侧那份状态会是**陈的**。好在卡上**已经在算**这个包围盒（§12.4 的每子步归约）
   ⇒ 补一次 **24 B 回读**即可。

⇒ **建议的接法（选项 A：先只接"纯 2b 流体"）**：给 `World` 加一个"该流体的步进在卡上"的标记（与

**选项 B（应用层持有）**：`World` 不动，App 在 `World::step` 之外接手流体那一相——零侵入，但耦合时序

两句实话：选项 A 要动 facade（`world_struct.rs`/`world_step.rs`）与 fluid crate 的可见性，**本机跑不了
CI 的 GPU 路径**（CI 无适配器）⇒ 只能靠 `gpu_body_probe` 那套对拍在本机守；这就是它存在的意义。

### 13.8 facade 接线**已落地**（选项 A，2026-09-24）

**四件套**：
1. **`vxl_phys_core::interop::FluidStepper`**（新 trait，落在 core ⇒ **两端都依赖 core**，不动任何依赖边）：
   `step` / `reactions` / `bounds` —— "推进 + 聚合整段交出去"的最小契约；实现者**自己拥有流体状态**。
2. **`World::set_fluid_stepper(fi, st)`**（facade）：注册后该流体的 `fluid_pass` 走卡上，主机此后**只**

   （`Packet::read_box`：**24 B 回读**卡上每子步已算好的那个，§12.4）；2a 介质采样对该流体**自动让位**
   （主机状态不再推进）。
3. **`GpuFluidStepper`**（GPU 档）：`Packet` + `ReactionStage` + **契约核对**（tick 必须 1/60、流体前缀与

**验收（新探针 `gpu_facade_probe`：静态盒体容器 + 8³@0.05 水块 + 浮盒 ρ=400；150 tick；两条链

### 13.9 卡上包围盒改报**紧凑 AABB**（2026-09-24，§13.8 的"已知边界"收窄）

**改了什么**：`bbox.wgsl` 的 `box_setup` 多写 3 槽（`box_out[8..10] = 紧凑 hi`，位模式）⇒ `box_out`

零影响（**金样门三场景与冻结基线逐项相同**）。`Packet::read_box` 现在返回 **`(min, hi)` 真 AABB**

**残余差 = 1 子步行距（预期值，不是错值）**：卡上盒子由 `box_setup` 在**每个子步开头**写 ⇒ 读它时

**判据**（`gpu_body_probe` 新增第 ⑤ 行）：卡上盒 vs 主机按卡上状态算的 AABB ⇒
`min 差 2.94e-3 m / max 差 4.38e-3 m`，与"1 子步 × 0.8 m/s"同量级 ⇒ 确认是滞后；
`gpu_facade_probe` 读数不变（容器贴着水 ⇒ 近域集不受影响）。

### 13.10 提供者壁面的**镜像鬼影**上了卡（2026-09-24）

**分工（为什么不是纯卡上）**：provider 是体素/三角网/喷溅，**SDF 查询只有主机能做** ⇒ 主机跑
**同一个** `FluidSystem::wall_planes_in`（本片把它从 `pub(crate)` 提为 `pub`），把"每粒 ≤8 面
（接触点 + 外法线）"压成**稀疏三段**（`ids` / `start` / `planes`）上传；卡上 `wall_ghost.wgsl` 做
邻居遍历 + 镜像求和，与 CPU **同式**：`g = p_j − n·2·((p_j − pt)·n)`，`|p_i − g| ≤ h ⇒ Σ += k6(h²−r²)³`。

**调用点**：档位对象**由调用方持有**（`Packet::new_with_walls` 顺带建 `WallStage`——它绑 `items`/`dens`
两把只在建包那一刻拿得到的缓冲；`Packet` 字段数已顶门，见 §13.7）⇒ 每子步在**密度之后、EOS 之前**
`encode` 一趟（`run_stages_with(…, Some(&walls))`）。条目为 0 时是空操作 ⇒ 既有场景零影响。

**验收**（新探针 `gpu_walls_probe`：体素水槽 + 铸装水块，**同一状态比密度场**——零步长推进，
位置不动、只跑网格 + 密度）：

| 判据 | 读数 |
|---|---|
| 带鬼影：max \|Δρ\|（GPU vs CPU）/ ρ0 | **4.88e-7**（只剩浮点求和序 ⇒ 口径 B） |
| **金丝雀**（不带鬼影）：max \|Δρ\| / ρ0 | **2.92e-1**（mean 3.4e-2）⇒ 鬼影补的就是这一块 |
| 压制倍数 | ≈**6e5** |

**⭐ 一条重要的负面结论（先记下来，免得白追）**：**镜像鬼影单独托不住壁**。它只补 `0 < sdf < h`
那层的密度；挡住穿透的是 CPU 侧**每子步**的壁面投影（`boundary_pass`：SDF 查询 + 推出到静置线 +
法向速度归零），而投影是**主机侧**机制 ⇒ 本片没上卡。实测：让铸装水块在体素地上静置 150 tick，
**两条卡上链全穿地**（−18 m ✗；首版还从 0.05 m 高处落体，穿得更快）⇒ 判据因此改成"同一状态比密度场"
——那才是鬼影该负责的量。⇒ **provider 壁面场景暂时留在 CPU 路径**；要上卡得连投影一起搬
（卡上 SDF，或逐子步主机往返）——先算账再动。

**探针记录的操作坑**：CPU 侧要跑镜像，必须先把**壁面 provider id 表**交给流体（`sys.set_boundaries(&[v])`）
——首版漏了 ⇒ CPU 根本没跑镜像 ⇒ 与"无鬼影"档一致，把结论带歪了一轮。

### 13.11 壁面**投影**也上了卡（2026-09-24）——§13.10 的负面结论闭合

**接法（先算账的结论）**：逐子步"主机查 SDF → 上传 → 同步"**不可行**——每子步都要回读位置（4 次往返/tick、
8k 粒位置回读 288 KB/tick），结构上把 GPU 档的意义吃掉。可行的是**一张表两用**：
1. 主机收集的平面表**放宽到 `sdf < h`**（含穿透），且改用 `contacts_point_boundary`（**流体边界口径**：
   对 `sdf > 0` 与 CPU 镜像用的 `contacts_point` 等价，对 `sdf ≤ 0` 只有它给得对）；
2. 卡上两个入口共用这张表：`wall_ghost`（密度镜像，**核内**按 CPU 口径过滤 `0 < sdf < h`）与
   `wall_project`（投影，按 `pen > 0`：推到 `sdf = +skin`、法向速度归零、单次上限 h）。

**为什么够用**：体素/容器壁是**分片平面** ⇒ 平面在一个 tick 内不变 ⇒ 用 tick 起点收集的表做投影是
**精确**的（曲面壁近似）；时序放在**每子步积分之后**（与 CPU `substep` 末尾的 `boundary_pass` 对位）。
与 CPU 的已知差别两条：① 逐 tick 表 vs 逐子步重查；② **不做**"同位坍缩消解"（`separate_coincident`
那趟主机侧 O(k²) 小循环）。

**读数**（`gpu_walls_probe` 新增静置仿真段：150 tick、重力开、同一初值三条链）：

| 链 | 底层（最低 25%）平均 y |
|---|---|
| A CPU（镜像 + 逐子步投影） | **1.01350 m**（静置） |
| B 卡上（鬼影 + **投影**） | **1.01627 m**（与 A 差 **2.77e-3 m** ⇒ **水站住了**） |
| C 卡上（**只鬼影**，金丝雀） | **−18.88 m** ⇒ 穿地 ⇒ **投影不可省** |

密度对拍（①，带鬼影）在**放宽收集之后仍是 4.88e-7 ρ0** ⇒ 边界口径与 CPU 的 `contacts_point` 在
`sdf > 0` 一致（等价性有了实测支撑）。

⚠️ B 与 A 的**逐粒** `max|Δpos|` 0.393 m（512 粒 / 150 tick）：投影是**离散事件**（推出 + 速度归零），
一旦触发两条链的混沌就分道 ⇒ **判据看"站没站住 + 底层高度"（2.8 mm）**，别看逐粒轨迹。

### 13.12 刚体前缀的积分上卡（2026-09-24）

**是什么**：`integrate.wgsl` 的对应物（`body_integrate.wgsl` + `pipeline/bodies.rs::BodyStage`）——让
**体**也在卡上推进，与 CPU 同式：`v ← v + (g + F·inv_m)·dt` → 限速 → `ω ← ω + [R·((Rᵀτ) ⊙ l_local)]·dt`
→ 限速 → `x ← x + v·dt` → `q ← normalize(q + ½·dt·quat(ω,0)·q)`。世界系逆惯量在核内由"局部对角 + 姿态"
**现算**（与 `apply_world_inv_inertia` 同式，CPU 也是每次现算 ⇒ 无缓存依赖）；逐轴展开、不用内建
`dot/cross`（归约序未规定）。

**为什么单独一档**：本档只做"给定 `(F, τ, g)` ⇒ 推进一个 `dt`"，**不碰接触/解算/睡眠**（那些仍在主机侧）
⇒ 它是"全卡上跑一个世界"的**积分腿**，不是完整刚体管线。与流体各档同款：调用方持有、显式
`upload` / `encode` / `download`（`Packet` 字段数已顶门，见 §13.7）。

**验收**（新探针 `gpu_body_integrate_probe`：2 体（盒 2 kg / 球 1 kg）、240 tick、`dt = 1/60`、
重力 + 脚本 `(F, τ)` 序列 + 限速 50/40）：

| 判据 | 读数 |
|---|---|
| 前 5 tick | **逐位一致**（0.00e0） |
| 240 tick：`max\|Δpos\|` | **4.8e-7 m**（`\|pos\| ≈ 180 m` ⇒ **2.7e-9 相对**） |
| `max\|Δv\|` / `max\|Δω\|` | 3.8e-6 m/s（`\|v\| = 50 m/s` ⇒ 7.7e-8）/ 3.3e-6 rad/s |
| 体 0 **姿态夹角** | **0.000e0 rad** ⇒ 四元数路径逐位一致（Hamilton 积与 `integrate_angular` 的镜像写法正确） |

⇒ 卡上"**体 + 流体**"两条积分腿都在了；差的只是把接触/解算也搬上去（那是另一条大工程）。

### 13.13 编排：**两条积分腿 + 反作用**同一 loop（2026-09-24）

**做了什么**：`gpu_body_probe` 加 `--card-body` 档——GPU 链的**体也走卡上积分**（`BodyStage`）。于是卡上
一个 tick 的完整回路是：**上传边界段 → 流体子步 → 卡上聚合反作用 → 卡上体积分 → 新姿态**（姿态再回主机
重建边界段——那是 2b 的固有耦合，见 §13.7）。宿主积分档（默认）保留作对照：它只比"反作用"这条路，
`--card-body` 才把"体积分"也压到卡上。

**读数**（12³ 流体 + 挡板、240 tick、开放域闭合系统）：

| 判据 | 宿主积分（默认） | **体也上卡**（`--card-body`） |
|---|---|---|
| t=240 位移差 | 7.63e-6 m | **6.79e-6 m** |
| 末速 `vx` 相对差 | 1.98e-5 | **1.75e-5** |
| 两链动量账之差 | 1.98e-5 | **1.86e-5** |

⇒ 两条积分腿与反作用链**编得起来**，读数与"宿主积分"档同量级（差异落在口径 B 的噪声里）。
**成本口径**：每 tick 多一次体状态上传 + 一次回读（1 体 ≈ 2×112 B + 一次同步 ≈ 0.3 ms）⇒ 几百个体时按
`体数×112 B` 重算账；本片只验**语义**。

**留下的**：接触/解算/睡眠仍在主机侧 ⇒ 本片是"卡上世界的**积分腿 + 编排**"，不是完整刚体管线。

## 14. 接触/解算上卡：**先算账**（2026-09-24，尚未动手）

**规模**（`wc -l` 实测）：窄相 **4466** 行（`sat.rs` 443 / `simd.rs` 387 / `support.rs` 357 / `prims.rs` 155 /
`types.rs` 251 / `store.rs` 129 + 测试 835）、解算 **2679** 行（`solver_impl.rs` 614 / `joints.rs` 483 /
`types.rs` 219 …）、宽相 **1933** 行 ⇒ 合计 ≈**9k 行 CPU 逻辑**（搬或重写，二选一）。

**两个入口的形状**：
- `NarrowPhase::collide(bodies, pairs, heightfields, providers, out, jobs)`——**逐对独立、按对序追加流形** ✓
  （本来就走 `JobSystem` 并行）⇒ 天生适合"一对一线程"映射到卡上 ✓；
- `ImpulseSolver::solve(bodies, manifolds, config, dt, jobs)`——**岛 + warm start + 两趟**（带偏置趟 +
  无偏置趟）+ 岛级休眠 ✓；顺序冲量**逐约束串行**、warm start **跨 tick** ✗ = 卡上最不友好的一块。

**⭐ 决定性的约束不是性能，是确定性契约**：刚体侧在本仓是**逐位可复现**的（金样门冻结读数 + 三哈希 +
`m0_gates`/`determinism` 门），而卡上浮点**只能到口径 B**（§9.6 已判过）⇒ **解算整体上卡 = 刚体场景从
"逐位"跌到"容差"口径** ✗✗ ⇒ 只能做成**显式档**（像 2b / `--card-body` 那样），且**不得**改默认档任何读数。
这一条先钉死，再谈搬不搬。

**按"卡友好度"排的分解**：
1. **宽相**（挑 `grid_phase`/`wide` 那部分）：均匀网格/空间哈希天生并行 ✓ 但当前占比小 ⇒ 收益中等；
2. **窄相 `collide`**：逐对独立、输出按对序 ✓ 可卡上化 ✓ 代价是**四套几何都要移植**（SAT 盒 / 支持映射凸壳 /
   高度场 / 体素）——**工作量大头在这里**；
3. **解算**：与卡的模式冲突 ⇒ 两条路：**(a)** 保持主机侧（先做 1+2，结果回读 ✓ 推荐）；
   **(b)** 换**卡原生范式**（PBF/XPBD 投影式求解 ✓ GPU 友好 ✓）——那是**新档**，不是移植 ✓✓。

**收益这一笔**：卡上解算只在**大量刚体**（万级+）时才有意义（当前主机侧瓶颈在岛解算）；在那之前 1+2 的
收益也有限 ⇒ **裁决：本项在"目标是万级刚体场景"成立前不动手**。若成立，第一步 = 宽相 + 窄相的卡上对应物 +
**主机侧解算保留**，作为显式档接在 facade 后面；解算若真要上卡，优先 (b) 而不是移植顺序冲量。

**下一会话的入口**：§9–§13 是"流体 + 两体积分腿 + 壁面"的完整落地记录（每步判据/读数/踩过的坑都在）；
本节是"接触/解算"的起手账。**别在没读 §13 的情况下重推任何东西**——口径 B、`arrayLength` 段表、栅格映射、
尺寸门（棘轮管既有文件）的形状全在那里。

## 15. 壁面档接进 `FluidStepper`（facade 路径可用了，2026-09-24）

**接口**（`core/interop.rs` 的 `FluidStepper`）：新增 `fn gather_walls(&mut self, h: f32, providers: &dyn ProviderColliders)`——
**让后端自己去收集壁面接触**。这一条是踩坑后定的形状：第一版是"门面收集好、用 `set_wall_contacts` 喂进去"，
门面只能拿**主机那份脚手架**的位置（它不推进流体 ⇒ 全陈）⇒ facade 路径的浮盒差 **0.177 m** ✗。
改成"后端自己收"后：后端从**卡上**读位置（`Packet::read_state`），SDF 查询仍走主机侧的 provider
（`gather_wall_contacts`），差别立刻回到 1 cm 级 ✓。

**接线**（`world_step/fluid_stepper.rs`）：`fluid_stepper_pass` 里一行 `st.gather_walls(h, &self.providers)`
（空 `boundaries` 的纯 2b 场景里后端直接返回 ⇒ **零开销**，也**不做位置回读**）。

**验收**（`gpu_walls_probe` 新增 ③ 段：体素水槽（provider 壁面）+ 铸装水块 + **浮盒**（2b 推它）；
A = 整段 CPU、B = 步进在卡上，150 tick）：

| 判据 | 读数 |
|---|---|
| 浮盒 `y`（宏观量） | 1.27173 vs 1.26219（差 **9.54e-3 m** ≈ 体尺寸的 0.75%） |
| 浮盒 `vy`（瞬时） | −0.083 vs +0.195（差 0.28 m/s）——浮盒在起伏，这是**相位差** |

**判读**：同一场景里流体自身的口径 B 混沌（粒子级 `max|Δpos|`）是 **0.393 m**，而宏观的浮盒高度只差
**9.5 mm** ⇒ 与"纯 2b 档"（1.4e-5 m）相比松一档，但**远小于流体的自身混沌**。已知近似两条（§13.10/§13.11）：
① 平面表**每 tick 一张**（CPU 是逐子步重查）；② 不做"同位坍缩消解"。**要归因到哪一条需要消融**——用
**不起伏的重物**（如深插的柱体）替代浮盒，把"相位差"这一项去掉再比。

**⭐ 消融结果（同日晚些，同一探针 ③ 段）**：浮盒换 **重物**（ρ=3000 ⇒ 沉底静置）后：
`y` 差 **1.53e-2 m**、`vy` 差 1.43e-2 m/s（两侧都 ≈0 ⇒ 静置）⇒ **1.5 cm 不是"起伏相位差"** ✗，
是一项**系统差**。归因线索（两把**现成的尺**，不用新写场景）：

| 场景 | facade 路径 vs CPU |
|---|---|
| **纯 2b 容器**（`gpu_facade_probe`，边界粒子当墙） | **1.39e-5 m** ✓ |
| **provider 容器**（本探针 ③，体素墙） | **1.5e-2 m** ✗（≈1000×） |

⇒ **provider 壁面这条路**被指认（不是 2b、也不是 stepper 本身）。**下一步（便宜的判别）**：把该场景的
`substeps` 设成 **1** ⇒ "每 tick 一张平面表"就退化成"每子步一张"⇒ 若差消失 ⇒ 近似①（平面表新鲜度）；
若仍在 ⇒ 近似②（不做同位坍缩消解）或另有其因。

**⚠️ 那个判别法不可用（同日复核）**：本仓 `sound_speed = 10`、`h = 0.1` ⇒ `substeps = 1` 时
`c·dt/h = 10·(1/60)/0.1 ≈ 1.67`，**破声学 CFL**（配置注释写明要 ≤ ~0.5）⇒ 水会炸，量的就不是壁面近似了 ✗。
另两条想当然的消融也堵死：**关掉 wall 档**（`walls = None`）⇒ provider 容器里**没有任何投影**（投影是壁面档
的一部分）⇒ 水直接穿壁（= 已有的"金丝雀 C"现象）✗；**只关鬼影**则是 §13.11 已有的金丝雀（0.29 ρ0 密度亏损）✗。

**当前最好的读法（假设，附机制）**：facade 路径的 **1.5 cm 是"壁面路径的 2.8 mm 水位误差被**接触/缓冲双稳**放大"**
—— 体 0 在 A 链里**坐在地板上**（y = 1.0974 = 2.6 mm 穿透 ≈ 接触 skin），在 B 链里被**水膜托着**
（y = 1.1127 = 1.3 cm 悬空）⇒ "坐住 vs 托住"是个**双稳**判定，2.8 mm 量级的压力差足以翻转它。
**可检验的预言**：把体换成**浮体**（不发生地板接触，只有浮力平衡）⇒ 差应回落到 mm 量级——
早先那组"起伏浮盒"读数（9.5 mm）与之**方向一致但不干净**（起伏本身又引入相位差不干净）。
**要坐实需要**：一个**不起伏、不触底**的浮体（如带配重的竖直浮筒）+ 把**卡上**水线直接和 CPU 比
（现在只能比体的宏观量，因为门面在 B 链上那份流体是陈的脚手架）。

**✅ 补记三（同日，浮体验证）：预言成立**。把体换成**浮体**（ρ=800 ⇒ 不触底、跑到 400 tick）并改用
**末 40 tick 窗口均值**（浮体在极限环里：A 侧 400 tick 时 vy 仍有 0.18 ⇒ 单点差可能只是相位，
这是本仓已固化的纪律）：

| facade 路径 vs CPU | 差 |
|---|---|
| 纯 2b 容器（`gpu_facade_probe`） | 1.39e-5 m |
| provider 容器 + **浮体**（不触底） | **3.96e-3 m** |
| provider 容器 + **沉底重物**（有地板接触） | 1.53e-2 m |
| （对照）流体本身在**无体**场景下的水位差 | 2.77e-3 m |

⇒ **浮体的差（4 mm）≈ 流体自己的水位差（2.8 mm）** ⇒ 壁面路径的误差就是"水位差"这一个量；
**沉底重物的 1.5 cm = 同一个水位差被"坐住/托住"的双稳判定放大**（比 4 mm 大 4 倍）✓✓。
**结论**：facade 路径的差异**没有第三个来源**——归因到壁面近似的误差量级（水位 ≈2.8 mm），其余放大是
刚体接触的固有性质（不是 GPU 侧接线的错）。**真正的开放项**是把那 2.8 mm 再往下压：它对应 §13.10/§13.11
的两条近似（每 tick 一张平面表 / 不做同位坍缩消解），但已验过的判别路（`substeps = 1`）破 CFL 不可用
⇒ 需要另想一个**干净**的判别（或直接改近似本身）。

**✅ 补记四（同日，②b 对照）：那 2.8 mm **不是**"口径 B 的宏观噪声底"，是**真差**。** 同一场景把容器换成
**2b**（静态盒体当墙、**无 provider**、壁面档完全不参与）：

| 容器 | 底层平均 y 的 A/B 差 |
|---|---|
| **2b**（静态盒体） | **6.79e-6 m** |

**教训**：**"关掉某一档"的消融必须两侧同关**——只关一侧的对照测到的是"那一档的作用量"而不是"那一档的差"；
而 CPU 侧镜像与投影**共用一个 `boundaries` 开关** ⇒ 任何"只镜像"的对照都做不到对称，**别再设计这种实验**。

⇒ 于是"把 2.8 mm 压下去"确实不该再当目标（补记九的裁决成立）；但**投影的离散性本身可以改**（它是刀刃的
根源）——那属于"**投影精度**"这一项。

## 16. 投影精度（2026-09-24）

两项读数 + 一条机制；**结论：曲面壁的"表停滞"不是误差源，真正的刀刃是"静置层就坐在激活阈值上"**。

### 16.1 曲面壁的**停滞误差**：≈ 0（我的"片夹角尖峰"模型被否证）

**问题**：平面壁（体素/盒子）上"用 tick 起点的表做投影"是精确的（平面不动）；**曲面壁**上表里存的是
t=0 那片三角形的弦平面，粒子在一个子步里滑到相邻片上 ⇒ 推的方向可能用"上一片"的平面。
我的模型预测尖峰 ≈ **片夹角 × 推量**（n=16 时 3.9 mm、n=4 时 15.7 mm）。

**判据（纯几何账 ⇒ 确定性、无混沌；`gpu_curved_probe`）**：不跑仿真，对一组测试点算**两侧各自会给出的
推出**——CPU 口径 = 在**当前点**调 `contacts_point_boundary`；卡上口径 = 在**tick 起点** `p0` 收一次表
（`gather_wall_project_contacts`）再按 `wall_project` 同式算。R = 2 的圆槽、静置线 `+skin`：

| 片数 n | 片夹角 | 弦高 | **典型**（滑移 ≤1 cm） | **刻意跨片尖峰** | 模型预测 |
|---|---|---|---|---|---|
| 4 / 8 / 16 / 32 / 64 / 128 | 45° → 1.41° | 586 → 0.6 mm | **≤1.2e-7 m** | **0.000e0 m** | 15.7 → 0.5 mm |

⇒ **模型否证**：`TriMesh` 的 `contacts_point*` 给出的是**与查询点一致**的表面（近似/精确最近点），
滑移 1 cm 不会让两侧取到"不同的弦平面" ⇒ **tick 起点表对网格提供者不是误差源**。
**推论（省一笔）**：**不必**为此把投影表改成逐子步重收（那要多 8 次查询/tick）——账算不过来。

### 16.2 真正的刀刃：**静置层坐在激活阈值上**（②m；又否证了我自己的一个模型）

**我先前的模型**：投影是"`pen > 0` 就推到 `sdf = +skin`"（`fluid_boundary.rs:74` / `wall_ghost.wgsl:161`
同式）⇒ 静置层应在 `[0, +15 mm]` 里做**锯齿**（振幅 ≈ skin）。

**②m 实测**（CPU 单侧，无需显卡；逐 tick 打印**最低那粒**的 sdf，地板顶面 y=1.0）：

```
tick 1: +0.01219 | tick 2: +0.00679 | tick 3: +0.00059 | tick 4: +0.00026 | tick 5: +0.00057 …
tick 9: +0.00022 | tick 10: +0.00014 | tick 11: +0.00066 | tick 12: +0.00085 | tick 14: +0.00049
```

⇒ **锯齿模型否证**：层从静置线沉下来之后**停在表面上方约 0.2–1.6 mm**（不再弹回 +15 mm）——SPH 压力
已经把它托住了。⇒ 真实机制是**更狠的那条**：**层的平衡位置正好落在投影的激活阈值 `sdf = 0` 上**
（亚毫米级的脉动就会反复把粒子推过 0）⇒ 门槛式推出**间歇触发**，而"这一子步谁被推、推多少"由**机器精度**
决定 ⇒ 这就是 ②e（1e-8 自敏感就饱和）、②f（3.4 mm）、②i/②k（壁面档在场第一个子步就差）背后的**同一个机制**，
也解释了 ②b 的对照为什么干净（**2b 容器没有投影**，静置靠冻结粒子间的连续力）。

### 16.3 由此得到的改法候选（**需换代决策，不擅动默认档**）

把投影从"门槛式推出"改成**连续**形式（任选其一，都要先量化收益）：
1. **推到 `sdf = 0`**（真表面）而不是 `+skin`，并**只消法向速度**（把"接触"从"传送"变成"约束"）；
2. **按穿透比例的推出**（`push = pen` 而非 `pen + skin`）＋ 速度松弛；
3. **软约束/罚函数**（`k·pen` 的加速度，让静止位置可微）——最彻底，但要重新标定 `skin/α`。

⚠️ **代价面**：`skin = 0.15h` 与"静置在 sdf = skin"是**默认档**的既有口径（`fluid_access.rs` 注：
"接触带 0.15h：粒子静置在 sdf = skin 处，带越薄壁邻密度亏越小"）⇒ 改它**会动默认档冻结值与三哈希**
（金样门 `col45/pile5/tower25`）⇒ 按纪律属**换代**：要么显式换代（ADR + 更新冻结值），要么做成**可选档**
（像 GPU 档那样显式 opt-in）。
**先要的读数**（下一步，便宜）：改成候选 1 之后，量"**近壁层 sdf 的脉动幅度**"与"**②e 自敏感的饱和点**"
是否下降——这两个量能把"连续性收益"变成一个数。

### 17.1 相位账（**先量后改**：`m1_profile 8`，10k 静态 + 1k 动态、8 线程、近 60 tick 均值，perf-lock 独占）

**两条直接推论**：
1. **只搬宽相+窄相，上限 = 48%**（Amdahl；§14 的定性判断，现在有数）。要在万级拿到大倍数，

2. **回读不是瓶颈**（推翻了 §14 里"先做 1+2、结果回读"的隐含顾虑）：按固定槽布局算，7.3k 流形 ×
   ~64–104 B ≈ **0.5–0.75 MB/tick**，60 Hz 下 ≈ 30–45 MB/s，PCIe 3.0 x16 的 ~0.4% ⇒ **可接受**
   （流体档把回读压到 120 B/tick 是因为它只需要聚合量；接触的数据主机解算**确实需要**）。

### 17.2 切片顺序（按"可验证强度 × 收益"排，不是按代码量）

**第一片 = 宽相上卡**，理由三条：
- **占比 29%**（负载下第二大）；
- **可以做到逐位可复现**：宽相只吃**逐体 AABB**（6 f32/体，24 B）+ 格映射，纯比较/整数运算 ⇒ 与流体
  的网格相位同族（"整数相位逐位可同"，§9.6 已判过）⇒ **判据能做到"配对集合逐位相同"**，比口径 B 的
  容差判据强一档（这是本项目里最硬的判据形态）；
- 回读只有配对表（`(u32, u32)` 8 B/对；10k 接触 ⇒ 2–7 万对 ⇒ 0.16–0.56 MB/tick）⇒ 同一量级。

第二片 = **窄相上卡**（19%）：固定槽布局（每对一槽：`a|b|normal.xyz|n_points` + 4×`(point.xyz|depth|feature)`
≈ 104 B），**只移植能对上的一批几何**（球×球 / 盒×盒 SAT / 球×盒），其余对**主机侧回填同一槽位** ⇒
最终流形表 = 对序 ⇒ 结构确定 ✔；判据 = 逐对 `max|Δpoint|/Δdepth/Δnormal|` 走口径 B 容差，**feature 位
（整数）要求逐位相同**。

第三片 = **解算**：默认**留主机**；若要上卡，按 §14 的 (b) 走**卡原生投影式求解器**（新档），**不移植**顺序冲量。

### 17.3 铁律（沿用流体档那套，逐条照搬）

- **显式档**：注册/开关由调用方给（像 `World::set_fluid_stepper`、`--card-body`），**默认档一行都不走新路径**
  ⇒ 金样门三场景与三哈希**逐项不动**（刚体侧是逐位契约，卡上浮点只能到口径 B ⇒ 混进去就是破坏契约）。
- **每片都要有"能红的判据"**：第一片是**配对集合逐位同**（含金丝雀：故意改一个 AABB ⇒ 必须红）；
  第二片是逐对容差 + feature 逐位；第三片（若做）是**新档自己的**能量/落位判据（不与主机档比逐位）。
- **先量后改**：每片落地前先有 `m1_profile` 的同批读数（本节的表就是基线）。

2–3 倍，疑似时钟/驱动爬升）⇒ 只报范围、不报单值；要拿它当判据必须先按 `PERF_LOCK` 独占 + 多窗均值。

**⚠️ 这行**不是**"卡上更快"的证据**：① 本片只搬了球×球（4418 对里 3600 对，流形只占 950/1502），其余
仍走主机回填；② 每 tick 的**往返固定开销**（两次 `write_buffer` + `submit` + `poll`/`map`）在这个规模
上就是 0.3–0.5 ms ⇒ 它给"小规模下卡上档划不划算"定了个**地板**。战果要等几何族补全。

**本片不碰默认路径**（§17.3 铁律）：默认档一行都不走新路径 ⇒ §17.1 的相位账仍是有效基线，且

**下一步（第二片续）**，按分派表逐族补，**先盒×盒**（两侧都是盒 ⇒ 一槽 ≤4 点装得下）：

#### 17.9 补记：轴差异的**诊断工具已就位，定论还差一步**（同日）

往探针里加了 `axes_probe` + `axes_host`：对几何不符的前几对，**在主机侧用 core 数学复算 21 条分离轴**
（镜像 `sat.rs::build_axes` + 标量 sep 公式，含面轴序与 9 条棱叉积的压缩序），按 `sep` 降序打印前 5，
并标出"哪条是 CPU 选的、哪条是卡上选的"；体态取自**切档前的快照**（流形是在那一刻算的，事后读体态
已推进过一步 —— 这个坑修了）。

**首测读数（m1 档，对 (4365, 10947)）**：我的主机侧表里 `#0 棱12 sep=-5.687e-3`、`#1 A面2 sep=-5.832e-3`，
**卡上选的是 A面2**（表中第 2 名）；而 **CPU 的流形法线在我的表里连前 5 都进不去**。
⇒ **读数自相矛盾，不足以定论**：我手算同一条轴得到的排序还与复算表相反（说明**我的主机侧复算本身
可能有错**，或 CPU 那一对走的不是我以为的那条路径）。
⇒ **在把锅扣到核上之前必须先补齐这一步**：给**引擎侧**的 SAT 加一次性诊断（或在探针里**只喂那一对**
给 `DefaultNarrowPhase::collide`），把"CPU 选中的轴 + 它算的 21 条 sep"与我的复算表并排打出来。
**在那之前不能断定是卡上的错**（小档 0 条不符 = 至少没有普遍性错误）。`axes_host` 是下一轮的起点工具。

**✅ 补记二：量具**已验收**，矛盾因此反转成「可能不是卡的错」**（同日；`selftest` 已进探针）

先做了**量具自检**（这一轮最有价值的一步）：对 5 条**手算得清**的盒对，各跑一次「我的 21 轴复算表 #0」
与「**引擎自己**的 `DefaultNarrowPhase::collide`（单对、同一条代码路径、体态与快照逐位相同）」：

| 用例 | 引擎 | 复算 #0 | 判 |
|---|---|---|---|
| 轴对齐·X 浅叠 | n=(1,0,0) | A面0 (1,0,0) | **同轴 ✓** |
| 轴对齐·Y 浅叠 | 无接触 | sep=+5.00e-2 > skin | 一致 ✓ |
| 深叠·多轴近等 | n=(1,0,0) | A面0 (1,0,0) | **同轴 ✓** |
| 绕 Y 小角 | 无接触 | sep=+7.00e-2 > skin | 一致 ✓ |
| **m1 复现对 (4365,10947)** | **n=(-0.00162, 0.99999, 0) = 棱12** | **棱12 sep=-5.41e-3，n·=+1.0000** | **同轴 ✓** |

⇒ **复算表可用**（5/5，且含那个出问题的对）⇒ 上一节"复算表可能错"的怀疑**被否证**。

**矛盾因此反转成一个更锐的问题**：对 (4365,10947)，**引擎在隔离调用下选的正是 `棱12`（≈+Y）** ——
与**卡上选的那条一模一样**，也与复算表 #0 一致；可**全量跑**里同一条配对（同体号、同场景）CPU 的
流形法线却是 **Z 向**（`(-0.132, 0.0016, 0.991)`，1 点，`d=-0.00056`）。
⇒ **两边必有一方用的不是同一帧状态**：要么"切档前快照"不等于全量跑窄相看到的那一帧（例如那一趟的
流形其实是**复用**下来的旧表、来自更早的检测趟），要么隔离调用与全量跑的输入还有别的差异。
**⚠️ 方向因此改变：卡上那条（+Y）恰好与"引擎在给定帧上的答案"一致 ⇒ 先证明"全量跑与单对跑看到的是
同一帧状态"，再谈谁错；别先改核。**

**✅ 补记三：根因 = **子步**；"36 条"里的大半是**比了两个不同的帧**（同日，探针已修）**

`step()` 的结构是 `for k in 0..substeps { self.substep(dt, k == 0, reuse) }`，而 `substep` 里
**`detect = first || !reuse_manifolds`** ⇒ **非准静态时每个子步都重跑宽相+窄相**（`reuse` = 准静态才为真）。
⇒ tick 末留在 `manifolds` 里的是**最后一个子步**的表 —— 那一帧的输入**已经被前一个子步的解算 + 位置积分
推进过**。⇒ 探针"比两边流形"实际在**比两个不同的帧**：口径 B 的细微差经一步解算被放大，于是出现
"36 条几何不符"。**这与核无关，是判据自己没定住帧。**

**证据（探针自带的「同一帧证明」仪器）**：把该对分别按「切档前快照」与「事后(tick 末)」体态喂**引擎自己**
的单对 `collide` —— **快照帧给出的正是「卡上」那条答案，事后帧给出的正是「全量 CPU」那条答案**
⇒ 全量 CPU 的流形确实来自更晚的帧。（这条仪器现在常驻探针 `axes_probe`。）

**修法（探针侧，不动引擎）**：`cfg()` 里 **`substeps: 1`** ⇒ 窄相只在 **tick 起点**的位姿上跑一次
⇒ 与"切档前快照"**同一帧** ⇒ 判据才有定义。

| 场景 | 卡上档 t=1（子步=1） | 几何不符 | 金丝雀 | 窄相 ms/tick（默认 → 卡上档） |
|---|---|---|---|---|
| 小档 | **1.86e-9 m**（原 5.96e-8） | **0 条**（max\|Δn\| 6.7e-7 = ulp） | 3.48e-3 ✓红 | 0.105 → **0.250** |
| m1 档 | 4.90e-5 m | **24 条**（22 条法线变，max\|Δn\| 5.7e-3） | 7.81e-2 ✓红 | 0.507 → **0.817** |

⇒ 小档更干净（帧对了，t=1 降到 1.9e-9）；m1 档 36 → **24**，剩下的都是**近平行轴**之争：样本
`#0 棱22 z-倾 0.00351` vs `#1 B面2 z-倾 0.00422`（sep 差 **2.5e-4**）——**同一帧上仍选了不同的近平行轴**，
**成因未定**（是"真差"还是"次毫弧度级的近平行轴刀刃"，取决于那 2.5e-4 的 sep 差在两侧是否稳定）。

**下一步（入口已具）**：在同一帧上把**双方各自选中的那条在同一张表里点名**（`rank_of`：排第几 + 它的 sep），
并打出**前两名 sep 之差**：差落在 ulp 量级 ⇒ 刀刃（判据该容忍）；差在 1e-4 量级而双方仍选不同 ⇒
核里的轴集/sep 有**真差**（再查棱轴的构建与择优）。

**✅ 补记四：拿到了「卡上不是纯函数」的直接证据（同日；仪器已进探针）**

按上一节的入口做了两件事：
① **`▸ 点名`**：每对几何不符的流形，把**双方各自选中的那条**在同一张复算表里点名（排第几 + 它的 sep），
并打出**前两名 sep 差**；
② **卡上隔离**：把**同一对**（同一帧、同一个 2 体世界）单独喂给 `NarrowTier::run` —— 若全量跑与隔离跑
答案不同，就说明**卡上的逐对答案不是"这一对两体的纯函数"**。

m1 首条不符对 `(4570, 10942)`（子步=1，帧已定死）：

| 谁 | 选中 | sep | 与最大分离的关系 |
|---|---|---|---|
| CPU（全量） | **轴#0 `棱22`** | −9.889e-3 | = 最大（符合 SAT 取最大分离） |
| **卡上（全量）** | **轴#3 `A面2`** | −1.242e-2 | 比最大**低 2.5e-3**（≈ 2 万倍 ulp ⇒ **不是刀刃**） |
| 引擎（单对，两帧都试） | `棱22` | −9.889e-3 | = #0 ✓ |
| **卡上（隔离，同一对同一帧）** | **`棱22`（=表#0）** | −9.889e-3 | **= #0 ✓** |

前两名 sep 差 = **2.5e-4**；且**隔离下卡上选对、全量跑选错** ⇒ **卡上的逐对结果依赖这一对之外的什么**
（不是几何、不是 SAT 规则、不是刀刃）。

⇒ 疑点从"几何/SAT 规则"转到**核里逐 invocation 的状态**：最像的是 `sat_boxes` 里
`var axes: array<vec3<f32>, 21>` 这种**动态索引的局部数组**被后端降级到**共享/临时内存**（同 workgroup
内多个 invocation 互相踩），或某处索引越界**读到邻居对的数据**。
**下一步（决定性、且便宜）**：**前缀二分** —— 把真实对表按「前 m 对」喂给卡上、逐步加大 `m`，找出
"目标对的答案从 #0 翻到 #3"的那个 `m` ⇒ 直接点出**干扰对**，再从它反推是哪块状态被共享。

**❌ 补记五：头号假设（invocation 间干扰）被**否证**（同日）**

先做了最便宜的那个判别：把 `@workgroup_size` 从 **64 改成 1**（一排只跑一个 invocation ⇒ 同 workgroup
内**不可能**互相踩；核里的动态索引局部数组若真被降到共享内存，差异就该消失）。

读数：m1 档 **24 条几何不符一条不少、max\|Δn\| 5.71e-3 与改前逐位相同**；小档同样 0 条不变
⇒ **容器布局无关 ⇒ "invocation 互相踩"被干净否证**。（已把 `WG` 改回 64，并把这条否证写进
`narrow.rs` 的常量注释里，免得下次再试。）

**剩下的可能收窄到两类**：① **同一对、同一帧下卡上仍算错**（那就是 `sat_boxes` 的纯函数性有问题，
只是不靠容器布局）；② **"全量跑喂进去的输入"与"我的快照"不一致**（怀疑面转向**打包**：`pack_bodies`
用的是 `bodies.position[i]`/`rot(i)`，而 `Pose32`/`PoseArray` 是**打包存储**——若 `rot(i)` 有重构/规范化，
快照取的姿态就不是核读到的姿态）。⇒ **前缀二分仍是下一步**（它不依赖这两个假设谁对：若"前 m 对"里
目标对的答案随 m 变 ⇒ 是①；若恒定 = 隔离值 ⇒ 是②，且能把矛头指到打包/读表那条链上）。

**✅ 补记六：前缀二分**跑完了** —— 卡上是**纯函数**（假设①否证、②升级为主嫌）

**做法**（探针里的 `prefix_bisect`）：同一个两体世界、**同一对 `(0,1)`**，只让**对表长度 m**（因而目标对
的**槽位号 m−1**）递增 1→4096，每次读**最后一个槽**的答案，看 `n·#0`（越接近 +1 越对）。
**读数**：`m=1:+1.0000 m=2:+1.0000 m=4:+1.0000 m=16:+1.0000 m=64:+1.0000 m=256:+1.0000
m=1024:+1.0000 m=4096:+1.0000` ⇒ **一个不差、与 m 无关**。
⇒ **卡上对"这一对"是纯函数**：答案不依赖槽位号、不依赖邻居、不依赖批次规模。**假设①（卡上算错）被否证。**

⇒ **剩下的只有假设②**：全量跑喂进去的**输入**与我的隔离世界不同。嫌疑面收窄到**打包/读表那条链**
（`pack_bodies` → 核里 `a*BODY_WORDS` 索引 → `bodies.position[i]`/`rot(i)`/`shape[i]`）——
即"**全量跑那一趟里那两个体的记录**"与"我从快照重建的两体世界"不是同一份数据。

**下一步（很窄，且现在很容易验证）**：**把两边喂进去的记录逐字打出来对**——
① 在 `narrow_tier_pass` 里对目标对做一次一次性 dump（`pack_bodies` 后取那两个体的 12 字，`{:?}` 出来）；
② 探针同样 dump 它重建的那份（同 12 字）；
③ 逐字比。**逐字相同 ⇒ 问题在核读表的索引/半径；不同 ⇒ 问题在打包那一刻的体态**
（那就回头查"快照 ≠ 那一趟的体态"，即**帧**，用同样的逐字对拍把帧钉死）。

**❌ 补记七：追查收尾 —— 「卡上选错轴」是**我自己探针的错**（跨 tick 错配）；核被洗清**

按补记六的入口做了三件（记录逐字对拍 + 真索引对照 + 真对表复现），先把"喂进去的记录"这一栏钉死：
- `narrow_tier_pass` 加**默认关**的一次性 dump（`VXL_NARROW_DUMP=<a>:<b>:<tick>`）：**本趟真正打包给卡上**
  的那两个体的位姿/半长原样打出；
- 与探针**按快照重建**的那份逐字比：**完全相同**（含那个 ~180° 的四元数）⇒ **输入一致**；
- 真索引对照（把同两条记录放在**真实体号** 4570/10942、表撑到 10943 条）：与 `(0,1)` 隔离**逐位相同**
  ⇒ **与体号/表规模无关**。

**而真正的病根是取证时机**：`axes_probe` 原先放在 `run_pair` 的**240 tick 循环之外** ⇒ 它读的
`a.manifolds()` / `a.pairs()` 是**最后一个 tick** 的，却拿**首 tick 的快照体态**去复算
⇒ 一组**跨 tick 的错配**（首现"证据"里那条 `真对表复现（97 对，目标第 1 位）`就是末 tick 的 97 对，
而 t=1 有 **3942 对**、目标在第 1378 位）⇒ 于是"隔离跑对、全量跑错"看起来成立，其实两边根本不在同一帧。

**改到 t=1 当场取证后，结论反转**：

| 读数（t=1，真对表 3942 对） | 值 |
|---|---|
| `▸ 点名` | **CPU → 轴#2[棱01] sep=+1.1158e-4 \| 卡上 → 轴#2[棱01] sep=+1.1158e-4**（**同一条轴**） |
| `⌗ 隔离(0,1)` | n=(0.99997, 2.9e-6, −0.00784)（c2） |
| `⌗ 真索引(4935, 10017)` | **逐位相同** |
| `⌗ 真对表复现（3942 对，目标第 1378 位）** | **逐位相同** ⇒ **卡上在真对表下的答案 = 隔离下的答案** |

⇒ **核在"选哪根轴"上没有问题**：补记四里"卡上选 #3、比最大低 2.5e-3"那条**收回**（它是跨 tick 错配的产物）。
补记五（`workgroup_size(1)` 无变化）与补记六（前缀二分：答案与列表长度无关）用的都是**自洽的隔离跑**
⇒ 结论保留（"容器无关、纯函数"仍成立，只是不再需要用它们来指向一个不存在的 bug）。
**教训（与 §17.9 补记三同族，但更贵）**：**"同一帧"这条纪律要贯穿到取证本身**——我写下了"体态要用切档前快照"，
却把**取证调用**放在了循环外，于是拿了末 tick 的流形配首 tick 的体态。**取证必须在产生差异的那一 tick 当场做。**

**残留（真问题、但性质不同）**：t=1 仍有 **24/2616 条** `几何不符`，而**法线是同一条**（上表）⇒ 差在
**流形点集**（>1e-4 m）而不是轴 ⇒ 属于**裁剪/去重那条离散选择**一族（与 §17.7 的"集合口径"同源）。
**下一件实事的入口**：在 t=1 当场对那 24 条打**点集对照**（两侧的点、深度、feature），
判它是"同一批点的不同代表"（刀刃，判据该容忍）还是"点集真不同"（要查裁剪环）。

**✅ 补记八：残留 24 条**定性完毕** —— 刀刃族（**窄相卡上这一片收口**）

给 t=1 的诊断加了"**最近点距**"这一栏（每个 CPU 点到**最近**卡上点的距离）⇒ 读数：

| t=1（m1 档） | 值 |
|---|---|
| 几何不符 | **24 / 2616（0.9%）**，其中法线变 22 条，max\|Δn\| **5.71e-3**（次毫弧度级 **近平行轴**） |
| **最近点距 max** | **1.92e-2 m** ⇒ **< 去重间距 `min_sep = 0.04 m`** |
| 首条不符对的 `▸ 点名` | **两侧同选 `轴#2[棱01]`**，且**前两名 sep 差 = 0.000e0**（**精确平局**，被同一条规则解开） |

⇒ **残留 = 刀刃族**，两个来源都在 §17.7 判过的那一族里：① **SAT 的精确平局**（近平行轴 sep 相等 ⇒
选哪根都合法）；② **裁剪/去重的离散选择**（点距 ≤ 去重间距 ⇒ 同一簇换了代表）。**都不落在"接错线"上**
（结构、对号、点数、feature 多重集在 99.1% 的流形上全对；小档 0 条）。

**⚠️ 定性但**不**等于"可以忽略"**：这条读数说明的是**差异的性质**（等价接触的不同代表），不是"卡上可以
无脑接进默认档"——卡上浮点只到**口径 B**，默认档是**逐位契约**（§17.3 铁律不变）。

**§17 窄相线收口裁决**：
- ✅ **可验收**：① 结构/对号/点数/feature 多重集在可测范围内全对；② 小档 t=1 = **1.86e-9 m** 且几何
  0 条不符；③ 金丝雀（清空 count / 挪 1e-3 m / 挪 3 m）都如期变红；④ 连跑两次槽逐字相同；
  ⑤ 卡上档是**显式档**，默认档一行不走（三哈希 + 金样门逐项未动）。
- ⚠️ **m1 档残留 24 条刀刃族差异**（性质已定性、量级已给出），属于**口径 B 的固有**，不是接线错。
- ❌ **性能不成立**：两档都是卡上更慢（0.105→0.250 / 0.507→0.817 ms/tick，端到端口径含打包+回读+回填
  +装配；m1 档每 tick 打包 11k 体 = 528 KB）⇒ **"只把窄相搬上卡"的账是负的**。
- ⇒ **下一件实事不是继续搬几何族，而是一个决策**：要么按 §17.9 的结论做**状态常驻**（体数据留在卡上、
  每 tick 只回传增量，像流体档那样），要么**把这条线停在"正确但无收益"**、把力气放到别处
  （如 §16.3 的投影换代决策、`PLAN-boolean.md`、上帝对象门那 18 个长函数）。**这个取舍得由用户拍。**

### 17.10 取舍得**用户拍**：走"状态常驻"（体表增量上传 + 卡上散写）

**做法**（契约扩两条**带默认实现**的方法 ⇒ 别的后端不受影响）：
- `core`：`NarrowTierBackend::narrow_resident(bodies, changed) -> Option<()>`（`changed` = **记录有变**的体号，
  首帧/体数变化传全部；`Some` = 已同步并进入常驻模式）+ `narrow_run_resident(pairs)`（体表已在后端手里）。
- `gpu`：`upload_records` 把变动折成 `(体号, 记录)` **两段连续数据**（两次 `write_buffer`），再由核里新的
  **`scatter_records`** 写进常驻体表 —— 与主核**同一次提交**（省一趟同步；`n_upd = 0` 时整趟跳过 ⇒
  非常驻档零影响）。`resident_n`/`resident_upd` 两个原子记账。
- `门面`：槽里缓存**上一份整表**（`body_cache`）+ 每趟逐记录 diff ⇒ 只把变动交给后端；缓存缺失/行数变化
  ⇒ 本趟按"全部变动"（首帧与体数变化）。**未注册/跑不通/`predict_dt > 0` ⇒ 整趟回退 CPU**（铁律不变）。

**⭐ 关键读数（`gpu_narrow_up_probe`：同输入、同进程交替、窗口 30 均值、perf-lock 独占）**：

| 项 | 整表上传 | 常驻 + 变动 | 比 |
|---|---|---|---|
| 上传这一项（11k 体表 515 KB → 变动 751 条 35 KB） | 0.193 ms | **0.072 ms** | **2.7×** |
| 上传 + 跑（端到端那一段） | 0.584 ms | **0.463 ms** | 1.26× |
| 只跑（体表已常驻） | — | 0.391 ms | — |
| **自证**：整表 vs 常驻 **槽表逐位相同** | ✓ | ✓ | — |

**⭐ 两处"看着该快却只快一点"的根因（都留痕）**：① 第一版按**连续段合并**逐段 `write_buffer`
（段少时也才 1.4×）——**`write_buffer` 的代价按调用次数算**（515 KB 一次 ≈ 0.193 ms 而 35 KB 分多次
≈ 0.176 ms）⇒ 改成"**一次大上传 + 卡上散写**"才到 2.7×；② 上限也不止于体积：现在仍是 2 次
`write_buffer` + 一次散写派发 ⇒ 每次调用 ≈0.03 ms 是**地板**。

**⚠️ 端到端仍不赢（三次干净读数）**：m1 档 240 tick，CPU 默认 **0.496/0.520/0.538** ms/tick，
卡上档（含回填+装配）**0.804/0.825/0.892** ms/tick ⇒ **仍慢 ~1.6×**。**账已经能对上了**：卡上档自己那一段
（上传+核+回读）**0.463 ms ≈ CPU 的 0.5 ms**（**已到持平**），多出来的 ~0.35 ms **全在主机侧**：
① 每 tick **全量重打包**（11k 体 = 528 KB）；② **回读解码**（5081 槽 = 416 KB → `Vec<Slot>`）；
③ **回填 + 装配**（m1 场景有高度场 ⇒ 那批对必须回 CPU）。

**⇒ 下一批三个杠杆（按预期收益排，都还没做）**：
1. **只重打包动体**（静态体首帧后不再变 ⇒ 每 tick 只 pack 动体那 ~35 KB 而不是 528 KB）。
   ⚠️ **前提**：静态体的位姿**不能被程序改动**（改了就得整表重同步）⇒ 要么加一个显式的
   `narrow_tier_resync()`，要么在 `set_position` 类入口打脏标记（**做之前先想清楚这条**，别埋静默错误）。
2. **按需解码回读**（只解 `count > 0` 的槽，或直接把槽字切片交给装配，免建 5081 个 `Slot`）。
3. **装配/回填的批量化**（回填那批 hf 对已有一次调用；装配可以只搬用到的字）。

**本片**：`gate_all.sh` 全绿（显式档 + 默认档一行不走 ⇒ 三哈希与金样门逐项未动）；默认档侧零改动。

### 18.1 CPU 引擎在 10M 档的实测（2026-09-26，`sph_scale 215 4 T <threads>`）——**逐粒成本随规模退化 3–4×**

| 口径 | 300k（记录值） | **10M（实测）** | 逐粒成本对比 |
|---|---|---|---|
| 串行 ms/tick | 673.7 | **91 437.83**（91.4 s） | 2240 → **9201 ns/粒/tick ⇒ 4.1×** |
| 8 线程 ms/tick | 129.3 | **13 452.67**（13.5 s） | 430 → **1354 ns/粒 ⇒ 3.1×** |
| 并行加速比 | 5.2× | **6.80×** | 并行**反而更能扩**（不是并行坏了） |

**相位账（10M，8 线程）**：网格 633.64（4.7%）| 密度 **5961.81（44.3%）** | 压力 20.88 | 力+黏度 **6710.03（49.9%）**。
按线性外推（300k 并行值 ×33）算：密度该 1139 ms（实测 **5.2× 差**）、力该 2079 ms（实测 **3.2× 差**）、
网格该 851 ms（实测 633 ms，**比线性还好**）。
⇒ **退化的只有两个"邻域遍历"相位**（密度/力+黏度），而**网格相位不退化**——这正是**访存局部性**的签名：
300k 档的工作集（≈12 MB 邻域数据）还在缓存层里，10M 档 ≈400 MB 完全落到 DRAM ⇒ 每次邻居收集都是内存往返。
**这条结论顺带解释了两件事**：① 为什么"重排/局部性"那条刀（`PLAN-0.3` §6.3 微探针算出只值 1.3–1.5×）
在**小档**上不值——它在大档上才值钱；② 为什么 GPU 档的相对优势**随规模上升**：网格相位
301k 是 14.4×（§11），10M 变 **158.4 / 3.209 ≈ 49×**（CPU 网格 633.64 ms/tick ÷ 4 子步 = 158.4 ms 对 GPU 3.209 ms/轮）。

### 18.2 规模扫描（2026-09-26）：GPU 侧**逐粒成本是平的**、二维分派**零代价**，缺口在探针的 `time_gpu` 段

给 `gpu_tick_probe` 加了**分段计时**（`⏱ build_fluid / build_packet / run_drift / report_reactions /
time_cpu / time_gpu`——千万粒档没有这个读数就只能猜）+ 规模扫描（都 `ticks=1 --cpu-threads 8`、perf-lock 独占）：

| 档 | 粒数 | GPU 常驻 ms/tick | **逐粒** | 回读 ms | 整 tick 比值 | `overflow` | 漂移 t=1（Δpos/Δv/动能比） |
|---|---|---|---|---|---|---|---|
| 301k（§12.1） | 300 763 | 9.36 | 31.1 ns | +2.59 | 82.3×（对**串行** CPU） | 0 | — |
| **1.225M** | 1 225 043 | **29.30** | **23.9 ns** | 12.16 | **14.9×**（对 8 线程） | 0 | 0.0 / 5e-5 / 1.0000 |
| **4.25M** | 4 251 528 | **99.49** | **23.4 ns** | 28.68 | **14.8×** | 0 | 0.0 / 4e-5 / 1.0000 |
| **10M** | 9 938 375 | **934.16** | 94 ns | 85.26 | **13.9×**（含回读 12.7×） | 0 | 0.0 / 7e-5 / 1.0000 |

- **GPU 常驻 934.16 ms/tick**（20 tick × 3 次取最小：[934.16, 937.96, 940.84]）⇒ **1.07 FPS @ 9.94M 粒**
  （⚠️ **更正**：本节初稿把等效 FPS 误写成 10.7，量纲错了 10×——`ms/tick` 与"等效 FPS"是 `1000/ms`
  的关系，同档 CPU 打印的 `0.1 FPS` 就是这把尺）；含耦合回读 **1019.43 ms/tick（0.98 FPS）**；
  对 CPU（8 线程 12 985.9 ms/tick）**13.9× / 12.7×**。
- **判据全过**：`overflow` 0、NaN 0、漂移行 t=1 `Δpos 0.0 m / Δv 7e-5 m/s / 动能比 1.0000`（口径 B：同一物理、无发散）；
  **显存**：进程峰值 2031 MiB（含桌面基线 ≈878）⇒ **本档增量 ≈1.15 GB，远在 ≤4 GB 预算内**。
- 相位消融（ms/tick）：分箱 5.98 | 扫描/占位 10.81 | 规范化 22.60 | **密度 428.09** | EOS 2.77 | **力 475.29** | 积分 37.10
  ⇒ 两个**邻域相位占 89%**（与 CPU 侧同构）。

**⭐ 4.25M → 10M 掉 9.4×（逐粒 23.4 → 94 ns）的根因：网格被设粗了，不是内核回归**。10M 档的箱子是
**54³ = 157 464 格（≈63 粒/格）**，而 4.25M 档是 **81³（≈8 粒/格）**——邻域核扫 27 格 ×
每格粒数 ⇒ **候选量差 ≈8×**，与 9.4× 的耗时跳变对上（相位账也指向同一处：密度 +405 / 力 +475 ms）。
⇒ **根因在共享的箱子规则**：`vxl_phys_core::grid::grid_box`「格边从 h 起，**总格数超 `GRID_MAX_BINS`
则加倍粗化**」——10M 档域 10.75 m ÷ h(0.1) = 108³ = 1 259 712 格 **越过旧预算 1 048 576** ⇒ 格边加倍
到 0.2 m ⇒ 54³ ✓（4.25M 档 81³ = 531 441 ≤ 预算 ⇒ 保持 0.1 m ✓）。

**✅ 抬预算复测（同日）：`GRID_MAX_BINS` 1<<20 → 1<<21 ⇒ 10M 档 4.14× 提速，且默认档零变化**

| 10M 档 | 旧预算（54³，≈63 粒/格） | **新预算（108³，≈8 粒/格）** |
|---|---|---|
| GPU 常驻 ms/tick | 934.16（**1.07 FPS**） | **225.67（4.43 FPS）** |
| 含耦合回读 | 1019.43（0.98 FPS） | **311.82（3.21 FPS）** |

**零成本判别（先做后改）**：抬预算前先跑默认档三处机器无关判据——determinism `FINAL_HASH=0x711be572…`、
m0 压力哈希 `0x417be20a…`、金样门 col45 45/45 / pile5 2000/2000 / tower25 2396/2500
（Δpos 0.0034/0.0041/0.0950）——**一字未动** ⇒ 默认档没有场景越过旧预算（分箱逐位不变）⇒ **不是换代**，
是"大域场景免费提速"；代价只有 `bins` 4 → 8 MB（相对 10M 档 1.15 GB 显存是零头）。
⇒ **10M 档 934 → 226 ms/tick**，与"候选量 ÷8"的模型预测一致（密度 4.6×、力 4.3×）；按同一模型，
1.225M/4.25M 两档格边本来就是 h ⇒ 不受影响。
**剩下的账**：含回读 311.82 ms 里回读占 86.16 ms（28%）⇒ §17.10 那条"**减往返次数**"在千万粒档同样是下一根杠杆。

**复核（同日，抬预算后）**：`gpu_grid_probe 215 --cpu-threads 8` 在**新箱子**上重跑 ⇒ `start` **1 259 713 项**
（= 108³ 格 + 1）、`items` 9 938 375 项 **0 项不同**、**表哈希 CPU ≡ GPU `0x36e63242c53fd8f8`**、
`overflow` **0**、GPU **3.510 ms/轮**（54³ 时 3.209 ms ⇒ **格数 8× 只多 9%**）⇒ **抬预算在 10M 档既快又对**：
`bin`/`place` 走 `(65535, 3)` **二维分派**、`canon` 走 1.26M 格 / 19 683 组的一维分派，两侧逐位同表。

### 18.3 **"减往返"这笔账算清了：它不是可做的局部优化，而是架构题（≡ §17.10 的 (B)）**

读码 + 实测都指同一处。`Packet::run` 的**固定箱子**路径（§12.1 的读数口径）**已经是最省的形状**：

- 整 tick 的 4 个子步**编进一个 encoder**（`for _ in 0..substeps { encode_substep(..) }`）⇒ **一次
  `submit`**；回读只在 `tick_readback` 时做一趟 `copy_buffer_to_buffer`（120 MB）在卡上拷贝，
  卡外**一次 `poll_wait()`** ⇒ **没有可删的冗余同步**；
- `--box=follow` 那条是**每子步一次 submit**（+ 每 tick 一次 poll）——4 次 submit 的驱动开销在 10M 档
  是微秒级（对照：一路 4.13 ms/趟是"提交+映射+等"的**同步**成本，不是 submit 数量）⇒ **也不是杠杆**；
- ⇒ 10M 档含回读的 **311.82 ms** 里，往返的账是**数据搬运本身**：回读 120 MB（**86.16 ms**）+
  上传状态 240 MB（`write_buffer(pos/vel)`，≈24–50 ms）≈ **40%**。

⇒ **唯一的出路是"状态不出卡"**：只让**聚合量**过 PCIe（反作用 `(F, τ)` / 每体 `spans` / 边界与壁面更新），
这**正是 §17.10 的 (B)**——那边叫"流形不出卡"，这边叫"状态不出卡"，**同一套架构**（常驻句柄 + 只交换聚合）。
所以本轮的结论是：**"减往返" ≡ (B) 的第一片**，它需要 ADR 级拍板（换的是"宿主要不要每帧看到流体状态"
这条语义），不是拧微优化就能拿到的收益。

#### 18.3.1 补记：账拆开之后**上一段的结论要修正**——**回读机制本身**就值 3–7×（语义不用动）

三档实测能直接算出回读的**有效带宽**（`readback_b` 只搬 `pos`，12 B/粒）：

| 档 | 回读量 | 实测回读 | **有效带宽** |
|---|---|---|---|
| 1.225M | 14.70 MB | 12.16 ms | **1.21 GB/s** |
| 4.25M | 51.02 MB | 28.68 ms | **1.78 GB/s** |
| 10M | 119.26 MB | 86.16 ms | **1.38 GB/s** |

⇒ 本机 PCIe 4.0 ×8 实测能跑 ~10–13 GB/s ⇒ **119 MB 的物理下限 ≈10–12 ms，实测 86 ms ⇒ ~86% 是开销**，
不是带宽。开销构成（`measure_readback_ms` 逐句）：卡上 `copy_buffer_to_buffer`（VRAM→VRAM，≈0.4 ms）+
**两次 `poll_wait`**（一次等拷贝提交、一次等 `map_async` 回调——**第一次是冗余的**：映射回调本来就在拷贝完成
之后才触发）+ `map_async`/`get_mapped_range`/`unmap` 的映射舞蹈 + 驱动侧暂存拷贝。

**⇒ 可减的三档做法（都不碰语义，按代价排序）**：
1. **去掉那次冗余 `poll_wait`**（改动一行级；正确性靠"映射回调必然在拷贝之后"这条 wgpu 契约）；
2. **把回读做成"上一帧的异步回读"**（双缓冲 + 只在下一次真要读时才 `poll`）⇒ 86 ms 的传输/同步被
   226 ms 的计算**遮住**（宿主仍每帧拿到状态，只是晚一帧——渲染/耦合的通行做法）；
3. **换持久映射的暂存缓冲**（一次 `map` 常驻、按帧 `get_mapped_range` + `write` 读新数据；避免每帧
   map/unmap 的驱动往返）——这是最有希望逼近 ~12 ms 的一条，但要按后端分别验（DX12/Vulkan 的映射语义不同）。

**所以"减往返"其实有两截**：**卡外机制**（上面三条，语义不变、目标 86 → 12–30 ms）与**架构**
（"状态不出卡"，≡ (B)，需拍板）。**先做前者**：它是纯机械收益，而且做完之后 (A)/(B) 的账也更干净
（含回读 312 ms 若降到 ~240 ms，(B) 的增量收益就从"省 86"变成"省 ~240"）。

#### 18.3.2 再补记：**上一段的"卡外三条"被数据否掉了**——成本是"按字节计价"的，同步次数无关

把**已有**的四档回读读数放在一起看**每 MB 成本**（不需要新测）：

| 档 | 回读量（pos，12 B/粒） | 实测回读+同步 | **每 MB** |
|---|---|---|---|
| 125k（§12.1） | 1.50 MB | 0.99 ms | **0.66 ms/MB** |
| 1.225M | 14.70 MB | 12.16 ms | 0.83 ms/MB |
| 4.25M | 51.02 MB | 28.68 ms | 0.56 ms/MB |
| 10M | 119.26 MB | 86.16 ms | 0.72 ms/MB |

**跨 79× 体积，每 MB 成本恒定在 0.56–0.83 ms ⇒ 纯"按字节计价"，没有可观的固定项**。这条把 §18.3.1 的
三条猜法**逐条否掉**：
- **① 去掉冗余 `poll_wait`**：固定项若可忽略，它最多买到 **~0–3 ms**（不是 74）；
- **② 异步/上一帧回读**：能"遮住"的只是**同步等待**，而这里根本没有可观的同步等待——遮不住按字节的搬运；
- **③ 持久映射暂存**：理论上能改善每字节效率，但**必须先量**（现在的 1.4 GB/s 到底卡在"未缓存/WC 主机读"
  还是"驱动内部暂存拷贝"？两者同因不同路）——**在量到之前不许承诺**。

⇒ **真正与"每字节成本"同量级的杠杆只有两条**：**(a) 少搬字节**（回读只搬耦合真需要的部分——这是**语义**
问题：宿主/渲染要不要每帧看全量状态）；**(b) 换掉回读路径本身**（后端级工作，先量再动）。
⇒ 于是 §18.3 的原判**其实站得住**：**"减往返"的实质仍是 "别搬"（≡ (B)）**，只是理由从"同步太贵"换成了
"**每字节太贵（1.4 GB/s，比 PCIe 峰值差 8–9×）**"。**教训（记下来防重犯）**：**"拆账"要按体积做标度分析，
不能只看一次读数就归因给"同步/映射舞蹈"**——本节的 §18.3.1 就是这么误判的（一次读数 + 代码里看到两次
`poll_wait` ⇒ 把 86% 记到了同步头上，而四档标度一摆出来，同步项根本不存在）。

**三条结论（都实测）**：
1. **GPU 侧逐粒成本是平的**：1.225M → 4.25M 粒子 ×3.47、耗时 ×3.40（23.9 → 23.4 ns/粒）。这与 CPU 侧
   形成对照——CPU 在 10M 档**逐粒退化 3–4×**（§18.1），GPU 不退化（带宽富余 + 邻域遍历天然并行）。
   ⇒ **规模越大，GPU 档越划算**（这也是 §17.10 那个取舍要吃的账）。
2. **二维分派零代价**：4.25M 档 ⌈4 251 528/64⌉ = **66 430 组** ⇒ 已经走 `(65535, 2)` 的二维分派，
   而它的逐粒成本与 1.225M（1D）**完全相同** ⇒ 展平那行的访问序确实是连续的（`gid.y` 每加一 = 顺序跳
   `65535×64` 粒），没有引入任何访存代价。
3. **整 tick 管线验到 4.25M**（比 §18 的"只验到网格级"强一档）：`overflow` 0、NaN 0、
   漂移行 t=1 `Δpos 0.0 / Δv ≤5e-5 m/s / 动能比 1.0000` ⇒ 口径 B 的"同一物理、无发散"在 4.25M 成立。

**缺口已定死（不是引擎、不是 GPU）**：10M 档卡在探针的 **`time_gpu` 段**——它按设计跑 **100 tick × 3 次
取最小**（≈300 趟）。实测这段：1.225M = 25.4 s、4.25M = 88.2 s（≈线性），**线性外推到 10M ≈200 s，
实测 >480 s** ⇒ 下一片两件事：① 把那个 100 趟循环**按规模缩**（大档 10 趟就够"取最小"了）；
② 顺手看它有没有一处超线性（`time_gpu` 内部按 rep/tick/子步分段即知）。
**显存读数（本片顺带量到，item ②）**：10M 档进程峰值 **2031 MiB（含桌面基线 ≈878）⇒ 本档增量
≈1.15 GB**，远在 SPEC 的 **≤4 GB** 预算内（外采：`nvidia-smi` 在运行期间轮询峰值）。

**分段计时读数（10M，`--cpu-threads 8`）**：build_fluid **66.5 s**（= CPU 建场 + 5 趟静置，与 §18.1 的
13.5 s/tick 吻合 ⇒ 那 5 趟就是它的账）| build_packet 1.7 s | run_drift 14.3 s | report_reactions 0.0 s
| time_cpu 13.1 s | **time_gpu >480 s**。⇒ 上一轮"25 分钟没读数"的谜面就此闭合：**前五段一共 96 s**。

**顺带复测的既有档读数**（同日、perf-lock 独占）：125k 网格 **0.070 ms/轮**（CPU 2.436 ms/子步 ⇒ 34.8×）；
301k tick：GPU 常驻 **7.09 ms/tick**（3 次取最小 [8.27, 7.09, 7.13]）⇒ 对 CPU 相位口径 **87.2×**、含耦合回读
9.71 ms/tick（63.7×）。⚠️ 比 §11/§12.1 记的 0.204 ms / 9.36 ms **更快**，但**同批 CPU 侧也更快**
（618.84 vs 770.83 ms/tick）⇒ 属**环境/驱动状态差**（同机不同批），不是改动所致（**表哈希逐位相同**即证）。

## 19. 待裁决："宿主/渲染要不要每帧看到全量流体状态"——两种回答的落地清单（2026-09-26，勾选用）

来源：§18.3.2 的定案——回读是**按字节计价**的（0.56–0.83 ms/MB、1.4 GB/s，比 PCIe 峰值差 8–9×），
所以"减往返"只能靠**少搬字节**或**换回读路径**，而"要不要搬"是产品语义问题（渲染与碰撞的最低需求）。
下面把两种回答各自的**接口改动 / 判据 / 工作量**写清，直接勾。

### 19.1 回答**"要"**（保留逐帧全量回读）⇒ 只优化回读路径

**语义**：不变（宿主每帧仍拿到全量 `pos`；渲染/碰撞/破坏管线照旧）。

| 步 | 做什么 | 判据 | 工作量 |
|---|---|---|---|
| ① | **判清 1.4 GB/s 的真身**：`measure_readback_ms` 里**一个字节都没读**（`get_mapped_range()` 后直接 `unmap()`）就花了 86 ms ⇒ 成本在 `map_async`/`unmap` 段（驱动把**映射区间**搬进可映射堆）。判别法：把 `slice(..n*12)` 换成**只映射 1 MB**（`slice(..1<<20)`）——**耗时随映射区间线性下降** ⇒ 是"按映射区间拷贝"；**仍是 ~86 ms** ⇒ 是**整块 flush**（驱动行为，改不动） | 同档两次读数对比（1 MB vs 119 MB） | **半小时**（改 1 行 + 跑 1 次探针） |
| ②a | 若是"按映射区间拷贝" ⇒ **只映射真需要的区间**（需语义点头：渲染要不要每粒）| 回读 ms 降 + 网格表逐位同表 + 漂移表不变 | 小时级 |
| ②b | 若是"整块 flush" ⇒ 只剩**换回读路径**（持久映射暂存 / 后端专用读回）：**先量再动**，且可能白做 | 同上 + Vulkan/DX12 各验一遍 | 1 个会话起 |
| ③ | 无论哪种：把回读**挪出关键路径**（渲染用"上一帧状态"是行业惯例）⇒ 双缓冲异步回读把 86 ms 藏进 226 ms 计算 | 端到端 tick 降 + 判据不变（漂移表改成"比 N-1 帧"须显式写明） | 1 个会话 |

**诚实预期**：② 的收益**完全取决于 ① 的判别结果**（现在不承诺）；③ 能把"含回读 312 ms"拉到 ≈226–240 ms
（**遮住**而非消除）。

### 19.2 回答**"不要"**（宿主只要聚合量）⇒ "状态不出卡" ≡ §17.10 (B) 的第一片

**语义**：宿主不再逐帧拿全量 `pos`；PCIe 上只走**聚合量**（流体→宿主：反作用 `(F,τ)`/每体 `spans`；
宿主→流体：边界/壁面/体的**增量**更新）。渲染若要位置 ⇒ 渲染侧直读卡上缓冲，或"一帧延迟的异步回读"。

| 面 | 现状 | 要改什么 |
|---|---|---|
| 流体→宿主 | **已具备**：卡上聚合成每体 `(F, τ)`（§13.3 已验收） | 只需关掉"每帧全量回读"（`tick_readback=false` 是现成开关） |
| 宿主→流体 | 已有**增量写**（`coupling.rs` 的 `write_buffer(pos/vel, off)`） | 边界/壁面/体更新按"变动才写"（窄相档 `narrow_resident` 是同款先例） |
| `world_step` | **逐帧消费流体状态**的地方（AABB 更新 / 碰撞 / 破坏管线） | 改成"卡上聚合 + 宿主自己的体状态"；**逐个消费点盘一遍**（本项主要工作量） |
| 渲染 | 读 `positions()` | 一帧延迟的异步回读（同 19.1 ③，但这里能真的省掉关键路径） |

**判据**：① **金样门 + 确定性三哈希**（只要宿主不参与流体演化，哈希就不该动——**先跑这条零成本判别**）；
② 探针漂移表改成"只在真回读的那一帧比"；③ 端到端 tick + 显存读数；④ 联动场景实跑（挖洞 / 推水 / 破坏）。
**工作量**：**1–2 个会话**（world_step 消费点盘点 + 按需回读开关 + 探针适配）。

**收益（两条线各一处、一次架构）**：流体侧省 **86 ms（含回读 tick 的 28%）**；窄相侧省**每趟 4.13 ms 的
"提交+映射+等"（占 m4 档 95%）** ⇒ 正是 §17.10 (B) 那笔账，两线共用一套做法。

### 19.3 建议顺序（不管勾哪个）

**先做 19.1 ① 那半小时的判别**——它同时是 19.2 收益的**上界依据**：若 86 ms 是"按映射区间拷贝"，
(B) 省的就是这 86 ms 的绝大部分；若是"整块 flush"，(B) 省的是**全部** 86 ms 且 ②b 那条**彻底不必做**。

### 19.4 ✅ 判别的实测结果（2026-09-26，当天就做完了）——**"按映射区间拷贝"，且存在随缓冲走的固定项**

把 `measure_readback_ms` 加了"**映射区间可指定**"（拷贝恒为全量），两档各测一次：

| 档 | 全量映射（= pos 全量） | **只映射 1 MB** | 判定 |
|---|---|---|---|
| 10M（119.26 MB） | **84.44 ms** | **24.11 ms** | **按映射区间拷贝** ✓（省 60.33 ms） |
| 4.25M（51.02 MB） | 26.69 ms | 9.35 ms | 同样 ✓（省 17.34 ms） |

**拆成两项**（这次是直接实验，不是标度推断）：
- **边际项 = 0.35–0.51 ms/MB（≈2.0–2.9 GB/s）**——按**映射区间**计价（仍低于 PCIe 峰值 10–13 GB/s 约 4–6×）；
- **固定项 = 随"缓冲总大小"走**：10M 档 1 MB 映射要 24.11 ms、4.25M 档 9.35 ms ⇒ ≈ **0.19–0.20 ms/MB 缓冲**
  （机制猜测：驱动对**整个映射分配**的失效/页表处理，与区间无关）⇒ **换回读路径/换小暂存缓冲才动得了它**。

**⇒ 三条结论**（修正 §18.3.2 与 §19.1 的表述）：
1. **②a 成立且值得做**：10M 档映射 1 MB = 24 ms 而全量 = 84 ms ⇒ **只映射真需要的部分**是真收益
   （若耦合只要 10% 的粒 ⇒ ≈24 + 6 = **30 ms，比 84 快 2.8×**）。**需要你点头"渲染要不要每粒"**。
2. **②b（换路径）从"可能白做"变成"值得一试"**：因为固定项 ~0.2 ms/MB 缓冲与区间无关 ⇒
   **缩小暂存缓冲**（分块拷/小 staging）能把它压下去；但代价是多次 sub-copy，需实测取舍。
3. **§18.3.2 的"纯按字节、无固定项"被否证**（那是 4 个粗点的标度推断，直接实验一测就有 24 ms 的 floor）
   ⇒ 教训升级：**标度推断只能用来"排除"，不能用来"定性"；定性要靠定向实验**（这次两档 × 两区间共 4 个读数就定死了）。

### 19.5 ✅ "要全量"这条的第三条（③ 挪出关键路径）**已落地并实测**（2026-09-26）

**做法**（`Packet` 两个新东西，默认关 ⇒ 默认档与既有判据不可能变）：
- `defer_readback: bool`（默认 `false`）：为 `true` 时 `run(.., tick_readback = true)` 只**发起**
  （末子步 `copy_buffer_to_buffer` + `submit`）就返回，**不调 `poll_wait`**；
- `readback_pending_wait()`：宿主在**真要读之前**（下一 tick 的计算已发出之后）调一次等完
  ⇒ **回读的等待与下一 tick 的计算重叠**（渲染/耦合用"上一帧状态"是行业惯例；每帧仍拿到全量状态，只晚一帧）。

**实测**（探针 `--pipe` 档；10M 档、同一装置/同一状态、perf-lock 独占）：

| 口径 | ms/tick |
|---|---|
| 同步档合计（计算 + 回读） | **292.89**（214.78 计算 + 78.11 回读） |
| **管线档（③）** | **227.70** |
| **收益** | **−65.19 ms ⇒ −22.3%** |

### 19.5.1 ⚠️ **上面那个 −22.3% 是低报（我自己的口径错，同日更正）**

上表的"管线档"只测了**等待**（`readback_pending_wait()`）——**没测真消费方那一步**：宿主拿到数据
还得**映射 + 把 119 MB 拷进 `Vec<f32>`**。补上 `take_deferred_state()`（等 + 映射 + 拷出）后重测：

| 口径 | ms/tick |
|---|---|
| 同步档合计 | **286.05**（207.74 计算 + 78.31 回读） |
| **管线档（真消费方：等 + 映射 + 拷出）** | **257.71** |
| **真实收益** | **−28.34 ms ⇒ −9.9%** |

**⇒ 那 78 ms 的真实结构**（比 §18.3.x 的"按字节计价"再细一层）：
**~28 ms 是 GPU 侧等待/同步**（可被下一 tick 的计算遮住）+ **~50 ms 是 CPU 侧 map + memcpy**
（把 119 MB 从**未缓存**的映射区拷进主机 `Vec` ⇒ 有效 ~2.4 GB/s，正是 §18.3.2 那 1.4 GB/s 的来源）。
⇒ **剩下那 50 ms 不在 GPU 关键路径上，但在 CPU 关键路径上** ⇒ 下一刀按代价排：
① **并行解析**（`thread::scope` 分块拷出，6–8× ⇒ ~7 ms）——**语义零改动，最省**；
② 不拷出（消费方直接读映射切片——要改消费方）；③ 少搬字节（语义，见 §19.1 ②a）。

⇒ 78.11 ms 的回读**几乎被完全遮住**（残余 ~13 ms = 管线填充/排空那最后一趟等待，不可遮）。
同批复测的回读判别不变（全量 78.11 vs 只映射 1 MB 21.69 ⇒ 仍"按映射区间拷贝"）。

**⚠️ 投产时的语义**（写清楚，别埋静默错）：管线档下宿主拿到的是**上一 tick 的全量状态**——
渲染无感，但**若耦合解算要用"本 tick 的流体状态"就得显式接受一帧延迟**（或只在需要处同步一趟）。
⇒ 建议：门面按"渲染用管线档、耦合用同步档"分档接线；`--pipe` 现在只是**演示档**（探针默认走同步）。

## 20. 下一根杠杆（"压邻域访存"）的**先算账**（2026-09-26）——不需要新测量

§18.2 那条"226 ms 里密度+力占 92%"要往下走，先得知道这 92% 里**有多少是"每粒固定工作"、多少是
"候选量收集"**。这两项**用已有的两档消融读数就能解出来**（细格 108³ ≈8 粒/格 vs 粗格 54³ ≈63 粒/格，
同 10M 粒、同 4 子步）：

| 相位（10M 档） | 细格（k ≈ 216 候选/粒） | 粗格（k ≈ 1701） |
|---|---|---|
| 密度 | **93.82 ms** | **428.09 ms** |
| 力段（力+黏度，`力 − 密度`） | **115.93 ms** | **478.07 ms** |

按 `t = a + c·k` 解两组方程（k 取上表的估算值即可，两点的**比值**才是判据）：
- 密度：`a ≈ 45.2 ms`（48%）、`c ≈ 0.225 ms/(候选·粒)` ⇒ 细格上 **48% 固定 / 52% 候选**；
- 力段：`a ≈ 63.2 ms`（55%）、`c ≈ 0.244` ⇒ **55% 固定 / 45% 候选**；
- **合计（209.75 ms）= ~108 ms 每粒固定工作（52%）+ ~101 ms 候选量收集（48%）**。

**⇒ 由此得到两条杠杆各自的上限（都写在"先算账"口径下）**：
1. **候选收集（~101 ms）**：共享内存按格分块（27 格协同载入）能砍的是**访存重复**——上限 ≈ 把它砍到
   一半 ⇒ **约 −45 ms（对 226 ms 整 tick ≈ −20%）**；
2. **每粒固定工作（~108 ms）**：读自己的 pos/pmass、核函数/累加器的算术 → SIMD/减少指令——上限
   ≈ **−35 ms（≈ −15%）**；
- 两条都做 ⇒ **226 → ~145–160 ms（−30~35%）**。

**⇒ 为什么先做这个算账**：它把"哪条值得做"从猜变成算术，而且**判据现成**（网格表逐位同表 + 整 tick
漂移表 + 10M 读数）。⚠️ 两条都**只改核内**（`density.wgsl` / `force.wgsl` 的遍历与算术），不碰跨设备
语义 ⇒ **不需要拍板**；但**必须逐档复验**（细格/粗格两档都跑，因为这两档的收益结构不同：粗格档
候选项占比更大 ⇒ 分块收益更高）。

## 21. §20 的**前提被否证**，但换出一个更大的杠杆（2026-09-26，当天勘察完）

一句话：§20 打算用「workgroup 按格分块 + 共享内存」去砍那"48% 候选收集"，**这个前提不成立**——
粒子数组是**索引序**（`grid.wgsl` 的 `place` 写的是 `items[slot] = i`，`UniformGrid::rebuild` 也不重排
数组），所以一个 workgroup 的 64 个线程在空间上是散的、**没有可共享的邻域**。但同一次勘察换出一个
更值钱、更可做的读数：**代价的真身是「槽位 → 空间位置」的映射（访存局部性），不是"格内复用"**。

### 21.1 判别实验：`gpu_layout_probe`（**零内核改动**）

关键设计：**同位置、同工作量、只改"槽位 → 空间位置"的映射**，于是计时差就是局部性的纯效应：

| 档 | 槽位 k 放谁 |
|---|---|
| `natural` | 原粒子 k（**今天的数据路径**，`cell_items` 是任意置换） |
| `sorted` | 格序第 k 个粒子（**空间排序的理想档**：槽位序 = 空间序） |
| `random` | 随机置换（**完全没有局部性**的下界） |

**四条前提判据**（不满足就不许读数，全部实测通过）：
1. 三档 `cell_start` **逐项同**（同一位置集合 ⇒ 每格计数同）：1 259 713 项 ✓；
2. 三档**候选对数同为 2 092 132 666**（210.5 粒/粒）⇒ "工作量不变"被守住 ✓；
3. `bin_of` 与引擎同式（拿引擎那张**旧一个子步**的表当参照，差 ≤1 格 100%）+ **越界槽位 0**
   （越界非 0 就没收 27 格 stencil 的覆盖率）✓；
4. 三档表自洽 0 错位；`sorted` 档 `items[m] == m` 命中 9 938 375/9 938 375（理想档的定义）、`random` 档 2 ✓；
   物理对拍（分位对齐）≤ **2.8e-7** ✓。

### 21.2 读数（10M 档 = 215³ = 9 938 375 粒；箱 108³、格边 0.1 m；perf-lock 独占）

`c` = 密度 + 力两相位**每子步**的稳态耗时（两档 repeats 解 `t = c + R/r`，把与排布无关的固定项 `R`
——同步回读 28 B/粒 ≈ 180 ms——扣掉）：

| 档 | `c` ms/子步 | 相对 natural | p1/p2 ms | warp 邻域并集（格/线程） | 相邻槽步距 m |
|---|---|---|---|---|---|
| `natural` | **44.49** | 1.00× | 71.3 / 51.2 | 5.17 | 0.0996 |
| `sorted` | **28.49** | **0.64×** | 54.5 / 35.0 | 1.89 | 0.0767 |
| `random` | 3 303.01 † | **74.25×** | 3297.8 / 3303.0 | 26.62 | 7.1141 |

- † `random` 档的 `R` **解不出来**（一发跑满上百秒 ⇒ 降频 ⇒ 两档读数反过来、解出负 R）⇒ 表里给的是
  **两档原始值的较大者**，即 `c` 的**上界**（保守侧）。第一轮读数（r=(4,32)）复核：44.49/28.49/74.25
  三档为 **42.49 / 29.71(0.70×) / 3 364.37(79.18×)** ⇒ 两轮一致（≤8% 漂移）。
- 小档（n=60，216 000 粒）同法：`natural` 0.83 / `sorted` 0.72（**0.87×**）/ `random` 16.66（20.15×）
  ⇒ **档越小、局部性红利越小**（数据还在缓存层里）⇒ 这条杠杆**只在大档值钱**（与 §18.1 的 CPU 侧
  结论同族）。
- **标定**：`natural` 的 r=32 档读数 **51.2 ms/子步** vs 管线相位账 `(93.82 + 115.93)/4 = 52.44`
  ⇒ **差 2.4%** ⇒ 探针复现的就是管线的访问模式（那 7.2 ms 的差就是固定项 `R/32`）。

### 21.3 三条结论

1. **「按格重排」在 10M 档值 `1/0.64 = 1.56×`**（两个邻域相位 44.49 → 28.49 ms/子步）。两相位占整 tick 的
   92.8% ⇒ **整 tick 226 → ≈151–163 ms（−28 ~ −33%）**（外推，不是实测 tick）。它比 §20 猜的 −20%
   更大，但**机制不同**：不是"共享内存复用格"，而是 **① 去掉 `cell_items` 间接层 + ② 让 warp 的候选读
   合并**。
2. **局部性敏感度极大（74×），但流体并不到那个下界**。同一条场景往前推 600 tick 的诊断：

   | tick | 5 | 30 | 120 | 300 | 600 |
   |---|---|---|---|---|---|
   | warp 邻域并集 | 4.83 | 5.50 | 6.31 | 6.48 | **6.48** |
   | 相邻槽步距 m | 0.0987 | 0.1021 | 0.1142 | 0.1179 | **0.1180** |

   ⇒ **索引↔空间的关联只是温和退化（4.83 → 6.48）然后饱和**，离 `random` 的 26.62 / 7.11 m 有量级之差。
   物理原因：**SPH 是拉格朗日的**——邻居始终是邻居，粒子不会互相穿过。⇒ ① 既有 10M 读数
   （226 ms/tick）**是代表性的**（真实场景大概比它差 ~10–20%，按并集比例粗估），② `random` 那个 74×
   是**合成上界**、不是预报。（这也是对"拿晶格场景当验收仪器"这条做法的一次反检：它站得住。）
3. **§20 的另一半（"每粒固定工作" ~108 ms）没被这次实验触碰**，仍待做；但它的上限算法依赖
   `t = a + c·k` 那套两点法，而那套把"访存"与"算术"混在了一起 ⇒ 该重算（用本探针的两条诊断当自变量更干净）。

### 21.4 顺带修掉的两个**仪器静默失效**（都属于"读数看着像真的、其实在量空转"）

1. **`probe::PhaseParams._pad` 落在 shader 的 `n_total` 槽位上，而调用方传 0** ⇒ 两核的
   `if i >= P.n_total { return; }` **一粒都不算** ⇒ `gpu_density_probe` 一直在量空转（"耗时"里只剩回读）。
   已改名 `n_total`（**改名而非改值是有意的**：编译器会把每一处漏填揪出来）。
2. **`phases_on_adapter` 走一维分派**（`dispatch_workgroups(groups, 1, 1)`）：`n > 65535×64 ≈ 4.19M`
   就过 `max_compute_workgroups_per_dimension` ⇒ 校验错。核里那行二维展平早就在（`tests/dispatch_2d.rs`
   守着），只是探针没接 `split_2d`。

### 21.5 下一步（按"先算账"排，第一条是**成本侧**的账）

1. **量重排 pass 本身的成本**（本探针可扩一档：`--with-reorder`）。设计草图（**未量，别当已得**）：
   两核吃**按格排序的副本**（`pos_c`/`vel_c`/`press_c`，3 次 gather）+ `out_c` 散写回索引序
   （1 次 scatter）⇒ 4 趟 ≈ 1.5–2 GB/子步 ≈ **3.5–7 ms/子步**（毛收益 16 ms/子步）。
   **⚠️ 这个方案不碰宿主契约、不改内部索引空间**（排序只发生在"两核的输入副本"上），而且
   **逐位可同**（枚举序与算术一字未动，只是值从别处取）——所以它不是换代，是一条穿过 `Packet`
   内部的局部改动；**但"逐位可同"这条要拿判据验**，不许只靠推理。
2. **若重排成本吃掉毛收益的大头**，则备选是"**首次排序后每次只做近乎恒等的重排**"（近似有序 ⇒
   gather 近乎合并）——同样**先量**。
3. §20 的"每粒固定工作"照旧待做，但上限算法要重做（见结论 3）。
4. 生产场景的局部性曲线只量了**一条场景一个规模**（零重力 + 折叠剪切 + 固定箱，n=60）：真要做成
   断言，得在 ≥1 个真实场景（含边界粒子/体）上复测同两条诊断。**现在的口径是"一条场景实测 + 一条
   机理解释"，不是普适结论。**

   不改内部索引空间、枚举序与算术一字未动 ⇒ 逐位可同**（所以**不是换代**）。
2. **成本随错位程度涨、收益也随它涨 ⇒ 这条路在两端都划得来**：置换完全解耦时搬运涨到 29.18 ms/子步

   ⇒ **正则场景那条 +11.31 才是要用的数**，29.18 是护栏。

**⚠️ 一个测量坑（已修，价值在于它会静默给错数）**：`queue.write_buffer` 的**上传是在下一个提交里落地的**

同一次里 `R` 的护栏也把"不可解"档报成**两档较大者（上界）**而不是解出来的数。

1. **落地接线**（这条不再是"要不要做"的问题，是"怎么接"）：`Packet` 里多一条 reorder pass + 三张格序副本

3. 管线档（`run_deferred`）接进渲染路径（§19 的 −14.7%），与本条互不冲突、可叠加。

## 23. 接线的**准入判据**已立住：格序副本逐位复现（2026-09-26）

一句话：把两核改成"读格序副本"**不会动结果**——这条以前只是"论证"，现在是**逐位判据**（`gpu_layout_probe`
的 `equivalence_check`）。口径：`<档>[k]` 必须与 `natural[perm[k]]` **逐位相同**（dens / acc / xsph 三张表）。

| 档 | dens 不符 | acc 不符 | xsph 不符 | 判读 |
|---|---|---|---|---|
| `sorted`（n=60，216 000 粒） | **0 / 216 000**（maxulp 0） | **0 / 648 000**（0） | **0 / 648 000**（0） | 逐位复现 ✅ |
| `random`（同档） | 109 486 / 216 000（maxulp 5） | 361 146 / 648 000（516 096） | 446 342 / 648 000（1.2e9） | **必须报错**（见下） |
| **`sorted`（10M，9 938 375 粒）** | **0 / 9 938 375**（maxulp 0） | **0 / 29 815 125**（0） | **0 / 29 815 125**（0） | 逐位复现 ✅（≈7 000 万个分量全中） |
| `random`（同档） | 5 665 518 / 9 938 375（6） | 18 057 158 / 29 815 125（1.7e9） | 20 670 198 / 29 815 125（6.7e6） | **必须报错** ✅ |

- **机理**（为什么 `sorted` 能逐位同）：natural 的格内枚举是"**粒子索引升序**"，而 `sorted` 档的槽位序
  `perm = items` 恰好把**升序排列的同一批粒子**放在同一格内 ⇒ 两边的**枚举序列是同一串粒子**，逐条对应。
- **能否证**：`random` 档的槽位序与粒子索引序无关 ⇒ 它格内枚举的是**另一串粒子** ⇒ **它必须报出不符**。
  实测报了（且 ulp 量级巨大）⇒ **这条判据有分辨力**，不是"永远绿"的假灯。三档都报 0 才该怀疑判据坏了。

⇒ 于是接线的红线（**默认档冻结值与哈希不得动**）有了前置保证：副本是精确置换 + 枚举序不变 ⇒
默认档的 `state_hash`/漂移表/金样值**不该**变。而"该不该变"由**端到端判据**验（§23.1 第 6 步）。

## 24. ⚠️ 新发现：**2b 路径（流体 + 边界粒子）不是 run-to-run 可复现的**（2026-09-26）

**一句话**：同一个 `Packet`、**同一个设备**、同一份输入，`snapshot` 之后 `restore` 回初值再跑一遍
⇒ **流体段的速度仍有 ~30–340 个分量逐位不同**（**次数随机** ⇒ 扰动种子随机），位置与**边界段**全同。
**纯流体同设备两遍逐位相同**（控制组）⇒ 这条是 **2b 场景特有**，不是回读/设备实例的问题。

**判据（`crates/vxl-phys-gpu/tests/sorted_copies_boundary.rs`，两条都常驻）**：

| 测试 | 场景 | 结果 |
|---|---|---|
| `pure_fluid_same_device_rerun_is_bitwise_identical`（**控制组，判红**） | 纯流体，同设备两遍 | **逐位相同** ✅ |
| `mixed_scene_same_device_rerun_report`（**只报告**） | 流体 + 一块地板的 2b 边界粒子 | 流体段 **328 / 27648** 个速度分量不符（每轮不同），边界段 0 ⚠️ |

**已排除的候选（都是实测否掉的，不是推理）**：
- **格表溢出**（会让 `canon` 放弃规范化、把格内序留在原子占位的任意序 ⇒ 求和序随运行变）：
  实测该场景**最大格占用 8**，`cap = 512` ⇒ 不可能；
- **未初始化读**：`dens`/`bins`/`out` 每子步全量写；`press` 由 EOS 按**总数**覆盖（`E.n = cfg.n`）；
- **跨设备差异**（两次 `Packet::new(0, ..)` 落到不同适配器）：控制组逐位同 ⇒ 否；
- **回读/计时器**：同上 ⇒ 否。

**为什么这条比 §23.3 更要紧**：它影响**每一个** 2b 场景的可复现性——而 2b（刚体↔流体双向耦合）是
本仓的产品路径。凡"GPU 可复现/逐位相同"的说法，**今天只在纯流体下成立**。

**它同时卡住了 §23.3 的准入判据**：`new_sorted` 在混合场景下今天会静默退回平铺档 ⇒ "两档逐位相同"
退化成"同一条路跑两遍"，而那条路本身就不可复现 ⇒ **判据写不出来**（会随机红）。⇒ **§23.4 必须先于
§23.3**。

**下一步的查法（建议按序）**：
1. 做**两个 device 实例 + 逐相位掩码二分**（`run_stages` 的 7 位）——把"哪一相位开始产生不确定"夹出来；
2. 需要读中间量时，把 `dens`/`press` 从 `ExtraBufs` 那条路借出来（`build` 已把 `dens_b` 转交给壁面档，
   不必新开 API）；
3. 重点看这几处（按嫌疑排）：① 2b 路径独有的**原子累加**（若有，`f32` 原子求和是天然不确定的）；
   ② 边界粒子的 `dens` 极小 ⇒ `cj2 = press[j]/(rho_j·rho_j)` 的**极值/除零**附近的分支不稳定；
   ③ `canon` 之外的任何"按占位序"的下游读取（`items` 的规范化是否真覆盖了**全部** 2b 格）。
